  HOW THESE NUMBERS WERE COMPUTED, so a verifier does not repeat the silent-zeros
  path: every aggregate above was taken over ANSI-STRIPPED lines. The logs in this
  package are the raw run logs and still carry the escapes, and in the compact
  tracing format the escapes sit BETWEEN the key, the "=" and the value - so
  `park_entries=(\d+)` against the RAW text matches NOTHING and the whole table
  silently reads ZERO for every counter. It is a plausible-looking all-zeros
  result, not an error, which is why it has to be stated rather than left to be
  rediscovered. Strip first, then match:
      sed -E 's/\x1b\[[0-9;]*m//g' <log> | grep -E 'live loop park telemetry'
  The same rule governs every witness in this package (the recorder decision line,
  the free-run stamp, the build-path lines): strip, then grep the field.

PORTABILITY (evidence/portability-patch.diff) - 2 lines, 3 expansions
  macOS ships bash 3.2, where `set -u` makes an EMPTY array expansion an
  "unbound variable" error (measured on the box). run_workspace.sh sets
  `set -uo pipefail` and expands LEG_FLAGS (empty for the SPLIT leg),
  PACING_FLAGS (empty for fixed100) and CHRT_PREFIX (empty at chrt0), so BOTH
  legs aborted unpatched. Each is wrapped in the ${A[@]+"${A[@]}"} idiom the
  same file already uses at :1048. On bash >= 4.4 the two forms are
  behaviourally identical (both expand to zero words when empty), so the Linux
  rows remain comparable; the patch only stops bash 3.2 aborting.
  Two lane-local shims were also needed and are NOT in the measured path:
  `sha256sum` (macOS has none; wraps shasum -a 256, verified against the GNU
  reference digest) and `gtimeout` (no brew coreutils on the box; a python
  stand-in for GNU timeout, contract-tested 6/6 including whole-process-group
  reaping). The watchdog never fired on any row reported here.

THE iox2 FLOOR CELL IS A NON-RESULT (no number was minted, and none is shown)
  results_iox2_chrt0.csv carries 2 rows with EMPTY latency and
  achieved_rate_hz=did_not_sustain; the other 8 sizes have no row at all.
  From the cell's own log, 64 B: NOT SUSTAINED at 100 Hz (skipped 6669 of 2100
  grid slots), then 50 Hz (6251 of 2100), then 20 Hz (2025 of 2100) - ladder
  exhausted. Skips exceed the slot count because the counter accumulates every
  grid slot jumped; inverting it gives the real per-round-trip wall: ~42 ms at
  the 100 Hz rung, ~80 ms at 50 Hz, ~98 ms at 20 Hz, against single-digit
  MICROseconds for this cell on Linux. The process held 99.6 % CPU throughout,
  and the behaviour reproduced in an interactive foreground run, so it is
  neither a busy box nor an artefact of how this lane detached its jobs.
  It is reported as unmeasurable-at-fixed100 on this platform. A follow-up
  should run this binary under `--variant backtoback` (no rate limiter) at one
  small size: microseconds would place the defect in the paced sleep path,
  tens of ms in the round trip itself. That question does not touch the
  Cerulion rows above, which were measured by a different mechanism entirely.

REP-1 MONO WAS MEASURED TWICE, AND BOTH ARE KEPT
  The first rep-1 mono run began 36 s after a 10-core cold build, with the
  1-minute load average still at 3.02, and tripped the sustain gate at two
  sizes (1 KiB and 256 KiB). It was re-run ~1 h later on an idle box, on the
  stated criterion "measured on an idle box" - NOT "whichever looks better".
  The re-run did NOT remove the fallback: it MOVED it to 16 KiB. That refutes
  the load-tail hypothesis and shows the gate trip is INTERMITTENT on this box
  (3 trips across 60 mono size-runs). The re-run is the shipped rep 1; the
  first attempt's logs and .rate sidecars are kept in
  evidence/rep1-mono-first-attempt/ so the choice is auditable. Cost of the
  re-run, stated plainly: rep-1 mono is no longer time-adjacent to rep-1 split,
  so strict interleave-by-rep holds for reps 2-5 and not for rep 1.
