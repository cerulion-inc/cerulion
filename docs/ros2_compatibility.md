# ROS 2 compatibility

This page says which ROS 2 distributions Cerulion's two ROS 2 surfaces run on, what has actually been tested, and what is known not to work. The two surfaces are different pieces of software with different reach:

- `rmw_cerulion`, the `RMW_IMPLEMENTATION` that runs unmodified ROS 2 nodes on Cerulion's transport. Its reach is set by the ROS 2 C API (rmw, rcutils, rosidl) it is compiled against.
- `cerulion ros2 attach`, which discovers a robot's DDS topics and bridges them without any rmw or rcl linkage. Its reach is set by DDS wire behaviour (GID width, the type-description service).

Source references below are paths in this repository (under `crates/`, `tools/` and `examples/`); the line numbers move with the tree. Anything marked unconfirmed has no retained artifact behind it and is stated only as far as the evidence goes.

## 1. How the rmw is built, and why a deployed library is per distro

`rmw_cerulion` does not ship one binary for every distro. Its C ABI bindings are generated at build time from the ROS 2 headers of the distro that is installed on the build machine (`crates/rmw_cerulion/build.rs` lines 6 to 17). The build reads exactly three environment variables (`build.rs` lines 254 to 256):

| variable | effect |
|---|---|
| `CERULION_RMW_SYS_INCLUDE` | explicit include directories; a variable that names no existing directory fails the build (`build.rs` lines 835 to 865) |
| `AMENT_PREFIX_PATH` | every prefix whose `include/` carries the core ROS packages is used; the rmw, rcutils, rosidl, introspection, dynamic typesupport, type description and service headers are added per prefix (`build.rs` lines 868 to 933) |
| `ROS_DISTRO` | cross-checked against what the headers say, never used as the source of layout (`build.rs` lines 313 to 364 and 653 to 679) |

A build with real headers is the only supported deployment path; the tree's own comment calls it "the only ABI-safe path for a deployed librmw_cerulion.so". The release packages carry exactly that build: the Linux archives, the Debian package and the Homebrew formula on Linux install `librmw_cerulion.so` beside the `cerulion` binary, built inside the `ros:jazzy` image for x86_64 and arm64 by the release workflow (`tools/scripts/build_rmw_jazzy.sh`, which refuses a library whose build script did not report generated bindings), and every Debian package is installed in a clean Jazzy container and exercised with a talker, a listener and an rclpy identity check before it is published (`tools/scripts/verify_rmw_deb.sh`); the check deliberately does not run `ros2 topic echo`, because the ros2 CLI graph tools do not see Cerulion topics (section 4). The macOS packages carry no rmw because ROS 2 Jazzy publishes no macOS binaries; on macOS `cerulion ros2 run` and `cerulion ros2 launch` exit 69 with a message that says so. With no ROS installed, the crate falls back to committed bindings generated from pinned rolling clones of ros2/rmw, ros2/rcutils and ros2/rosidl (`crates/rmw_cerulion/src/ffi/vendored_bindings.rs` lines 4 to 13). That fallback exists so the crate compiles on a developer machine and in CI. It refuses to become a deployment: naming a distro through `ROS_DISTRO` while a header prefix is present makes the build fail rather than silently use the snapshot (`build.rs` lines 332 to 343), and a vendored library only admits `rmw_init_options_init` under `ROS_DISTRO` values of `lyrical` or `rolling`, or under no `ROS_DISTRO` at all (`crates/rmw_cerulion/src/era.rs` lines 692 to 734 and 1017 to 1059).

The build bakes the distro it was compiled for into the library (`CERULION_RMW_BUILT_FOR_DISTRO`, `build.rs` lines 230 to 251). At load time the rmw compares that claim with the runtime `ROS_DISTRO` and refuses a mismatch inside `rmw_init_options_init`, before any typed operation (`crates/rmw_cerulion/src/api/init.rs` lines 23 to 67; refusal text in `era.rs` lines 764 to 771). Distros with identical layouts are treated as one (`lyrical` and `rolling`); Jazzy and Kilted are kept apart because their `rmw_init_options_t` sizes differ (168 versus 160 bytes, `era.rs` lines 692 to 731).

A runtime that sets no `ROS_DISTRO` at all is judged by the era the library was built for (`era.rs` lines 984 to 1059). A library built for Jazzy or earlier passes: the environment makes no claim to contradict, and the bindings came from the headers the process runs against. One hole stays open there and is narrowed rather than closed by this rule: a library built for `jazzy`, whose `rmw_init_options_t` is 168 bytes, loaded by a Kilted process that names no distro is still admitted, and the `impl_` store lands past the caller's 160-byte struct. A library built for Kilted, Lyrical or Rolling from real headers refuses, at the same entry point and before the same first byte. These three lay out `rmw_init_options_t` at 160 bytes where Jazzy is 168, Kilted having dropped `localhost_only`, and from Lyrical on the introspection `MessageMember` stride is 120 bytes against Jazzy's 112; a process that is really running an earlier distro would have those structs written at the wrong offsets and crash at the first typed operation. The 160-byte layout is what carries Kilted, since it shares Jazzy's member stride and era rank and only the init-options size tells the two apart. The refusal names the baked distro, the variable that was not set, and the setup file to source, taken from the baked claim and rendered with real distro names: a claim that names one distro prints that distro's line (`source /opt/ros/<distro>/setup.bash`), and a claim that stands for a set of layout-identical distros prints each member, leaving the reader to source the one the process will run (`source the runtime distro's setup file: /opt/ros/lyrical/setup.bash or /opt/ros/rolling/setup.bash` for the Lyrical and Rolling pair). The vendored fallback library is the one exception, and deliberately so: a development machine with no ROS environment is its whole purpose.

### The exported entry points

The library exports 112 `rmw_*` functions and nothing else (31 in `api/misc.rs`, 28 in `api/pubsub.rs`, 19 in `api/guard_wait.rs`, 18 in `api/services.rs`, 8 in `api/init.rs`, 8 in `api/node.rs`). The inventory mirrors `rmw_iceoryx2` on rolling (`crates/rmw_cerulion/src/api/mod.rs` line 4). The rmw C API carries no version constant, so there is no single "rmw API version" to quote; what changes between distros is the set of symbols rcl looks up and the layout of the structs they exchange. The export set includes symbols that first appeared in Galactic (`rmw_qos_profile_check_compatible`, the network flow endpoint functions), Humble (`rmw_feature_supported`, the content filter functions and the callback functions), Iron (`rmw_take_dynamic_message`, `rmw_serialization_support_init`) and Jazzy (`rmw_event_type_is_supported`). Ten of them are compiled out WHOLE where the distro's headers do not declare the type they take, never stubbed, so the export set follows the distro: `rmw_event_set_callback`, `rmw_subscription_set_on_new_message_callback`, `rmw_service_set_on_new_request_callback` and `rmw_client_set_on_new_response_callback`, the two content filter functions and `rmw_feature_supported` (Humble), `rmw_qos_profile_check_compatible` and the two network flow functions (Galactic) (`api/misc.rs` lines 1268 to 1344; `api/pubsub.rs` lines 4138 to 4165; `api/guard_wait.rs` lines 2465 to 2522). A Foxy build therefore exports 102 and a Galactic build 105, not 112: Galactic declares `rmw_qos_profile_check_compatible` and the two network flow functions and lacks the seven Humble ones. Each lane reads the built library with `nm` and fails if a symbol on that distro's list is defined (`tools/ci/rmw-distros/gate.sh`), and a test derives every row's list from the guarded exports and the capability era table, so a new guarded export fails until each older row names it (`crates/rmw_cerulion/tests/rmw_absent_export_table_test.rs`). The three Iron and Jazzy symbols above take types that already exist on Foxy and Galactic, so they are still exported there and answer `RMW_RET_UNSUPPORTED`. Several of those return `RMW_RET_UNSUPPORTED`; the list is in section 4.

### What a distro with a different rmw API hits

Three failure classes, two of them now caught before they can crash a node:

1. **Struct layout drift.** The introspection `MessageMember` is 96 bytes on distros without `fetch_function`, 112 on Humble, Iron and Jazzy (Jazzy adds `is_key_` at offset 32 without changing the size), 120 on Lyrical and Rolling; the GID storage is 24 bytes before Iron and 16 from Iron on; `rmw_init_options_t` is 104 bytes before Iron, 168 on Iron and Jazzy, 160 from Kilted on (`crates/rmw_cerulion/src/ffi/era_pins.rs` lines 59 to 118, 177 to 196, 231 to 297; `docs/internals/rmw.md` lines 149 to 151 and 273). A library built for one layout and loaded into another passes `rmw_init` and then fails at the first typed operation: a Jazzy-shaped member stride walks over Foxy's smaller struct and faults in `strlen` under `rmw_create_publisher` (`era.rs` lines 5 to 11). The compile-time pins in `era_pins.rs` refuse a header set that contradicts the selected bindings, and the load-time distro guard above refuses a runtime distro that contradicts the baked claim.
2. **Missing symbols.** rcl resolves rmw entry points by name at load. A distro that looks up a symbol the library lacks does not fail the load; it logs a resolve error on every node start. That applies to `rmw_event_type_is_supported`, a Jazzy-era probe: omitting the symbol, rather than exporting it and returning false, makes rcutils log a resolve error at every node start (`api/guard_wait.rs` lines 2433 to 2437). The reverse direction, a library exporting symbols an older distro never looks up, is harmless.
3. **Layout inside rmw structs the library fills.** `rmw_subscription_t` gains fields across distros (rolling has `is_cft_supported`, Jazzy does not), so the rmw zeroes the struct and stores fields by name instead of naming every field (`api/pubsub.rs` lines 2374 to 2384). `rmw_publisher_options_t` is copied whole (`api/pubsub.rs` line 721). The first 40 bytes of `rmw_init_options_t` are the same on every distro and everything after them differs (`api/init.rs` lines 47 to 51).

Two further hard limits: the library is 64-bit only (`crates/rmw_cerulion/src/ffi/introspection_cpp.rs` lines 172 to 176), and the rclcpp typesupport bridge mirrors each era's `MessageMember` under the capability cfg that introduced its fields, so the C++ path resolves on every era, from Foxy's 96-byte member to Lyrical's 120-byte one (`introspection_cpp.rs` lines 10 to 28; `era.rs` lines 111 to 122). Every real-header build also cross-checks that mirror against the distro's own C++ header, through a `static_assert` in the compiled shim, which build.rs points at that header by searching for it under every include root it knows, so a flat, a per-package and a colcon isolated install all resolve it; a build that names ament prefixes and cannot find it fails rather than skipping the check. The vendored build has no such header, and its test skips the comparison rather than asserting agreement. One member kind stays out of reach on Foxy and Galactic: a `bool[]`, wherever it sits, including inside a nested message and in a service request or response. Their C++ generator emits no `fetch` or `assign` accessor for `std::vector<bool>` and leaves `get` and `get_const` null, so there is no way in; a message carrying one is refused per message, naming the member by its path, before anything is written into the destination, and every other message and the whole C path used by rclpy are unaffected (`docs/internals/rmw.md` lines 356 to 375).

## 4. What runs unmodified over the rmw, and the known limits

Runs unmodified, with evidence:

- rclpy and rclcpp nodes: the cross-process rclpy test in both directions (`crates/rmw_cerulion/tests/rclpy_xproc_test.rs`), the three rclcpp nodes of the `rmw_cerulion` cell in the latency suite (`benches/latency/ros2`), `move_group` and `ros2_control` in the MoveIt hero.
- `ros2` CLI verbs through `cerulion ros2 run` and `cerulion ros2 launch`: pass-through wrappers that set `RMW_IMPLEMENTATION=rmw_cerulion`, prepend the library directory and a minimal ament prefix so rmw discovery can load the library, add the heap hook preload, and exec `ros2` (`crates/cerulion_cli_engine/src/ros2_cmd.rs` lines 2 to 34, 2373 to 2420, 2498 to 2534; user docs `docs/user-api.md` lines 191 to 192). Unix only (`ros2_cmd.rs` lines 1228 to 1233), and in practice Linux only: the library ships in the Linux packages, and a missing library is exit 69 with an install-route remedy on Linux or, on macOS, the statement that ROS 2 Jazzy has no macOS binaries and the verbs need a Linux machine. No distro gate of their own.
- Launch files: the MoveIt hero starts through `ros2 launch` under the rmw (`examples/moveit_hero/entrypoint.sh` lines 84 to 93).
- MoveIt 2 with zero source edits: the scheduled workflow above plans with OMPL and executes the trajectory through `joint_trajectory_controller` over `rmw_cerulion` (`examples/moveit_hero/`).
- Parameters (they ride ordinary rmw services, `docs/internals/rmw.md` lines 537 to 538), services (18 exports, e2e in `docs/internals/rmw.md` line 1080), guard conditions and `rmw_wait`, TRANSIENT_LOCAL late-joiner delivery with a raised subscriber ceiling (`docs/internals/rmw.md` lines 436 to 439 and 1058 to 1065). Actions have no rmw-level API; they run as the topics and services beneath them, and the MoveGroup action is what the MoveIt hero exercises.
- Zero-copy publish and take need the Jazzy opt-in `ROS_DISABLE_LOANED_MESSAGES=0` and the heap hook the `ros2` verbs preload (`libcerulion_heaphook.so`, shipped beside the rmw in the Linux packages) (`api/pubsub.rs` lines 2387 to 2388; `docs/internals/rmw.md` line 772); without them the rmw takes the copy path.

Known limits:

- **Endpoint discovery is process-local, so the ros2 CLI graph tools do not see Cerulion topics.** `rmw_get_publishers_info_by_topic` and `rmw_get_subscriptions_info_by_topic` answer from the process's own registry, and so does the graph query behind `ros2 topic list`, `ros2 topic echo` and `ros2 node list`. In a Jazzy container with a live `demo_nodes_cpp` talker, `ros2 topic list` (with and without the daemon), `ros2 topic echo --no-daemon` with an explicit type, and rclpy's `get_topic_names_and_types()` from a third process each see only that process's own `/parameter_events` and `/rosout`, never `/chatter`, while a second `cerulion ros2 run demo_nodes_cpp listener` receives it (pub/sub rendezvous is by name on the shared-memory service). Inspect Cerulion topics with `cerulion topic list` and `cerulion topic echo`, which read the shared-memory plane; cross-process endpoint discovery is not implemented (`docs/internals/rmw.md` lines 1070 to 1072 and 1085).
- **Multi-node graphs need an `iceoryx2.toml`.** Every ROS 2 node publishes on `/rosout` and `/parameter_events`, and iceoryx2's default caps publishers per service at 2, so a third node dies at startup unless the cap is raised; the MoveIt hero image installs a config raising publishers and subscribers to 32 and event ports to 64 (`examples/moveit_hero/README.md` lines 131 to 141; `examples/moveit_hero/iceoryx2.toml` lines 22 to 34; `api/pubsub.rs` lines 1061 to 1072).
- **SROS2 is not supported.** The rmw contains no handling of `ROS_SECURITY_*`; the security options rcl fills are carried in the init options and never consulted (`api/init.rs` lines 51 and 174). Setting `ROS_SECURITY_ENABLE=true` does not secure a Cerulion transport, and the rmw neither honours nor explicitly refuses it.
- **Unsupported entry points return `RMW_RET_UNSUPPORTED`** wherever the distro declares them; the ten that a Foxy build does not export at all are listed in section 1. Publisher and subscription events and their callbacks (`api/guard_wait.rs` lines 2408 to 2522), the new-message, new-request and new-response callbacks (same range), content filters (`api/pubsub.rs` lines 4138 to 4165), publisher and subscription allocations (`api/pubsub.rs` lines 2106 to 2115 and 4177 to 4194), network flow endpoints (`api/misc.rs` lines 1318 to 1344), dynamic messages and `rmw_serialization_support_init` (`api/misc.rs` lines 489 to 531), `rmw_get_serialized_message_size` (`api/misc.rs` lines 225 to 232). Loaned messages are refused for non-loanable types and when the heap hook is absent (`api/pubsub.rs` lines 1326 to 1328 and 1456 to 1458).
- **Platforms:** 64-bit Linux and macOS only (`README.md` line 84; `introspection_cpp.rs` lines 172 to 176). No Windows. The released rmw library is Linux only (x86_64 and arm64, built on Ubuntu 24.04); the macOS run in section 2 used a library built by hand against RoboStack headers, which no package ships.
- **Two vendored message types hash-skew against a stock Jazzy robot** (`control_msgs/PidState`, `control_msgs/SteeringControllerStatus`; `docs/internals/native-ros2-messages.md` lines 145 to 148); resolving the schema from the robot through the attach wire rung is the remedy.

Some runs cited above have no artifact in this repository: the four ROS 2 regression lanes, the distro guard, the Go2 attach, the macOS arm demonstration and the Foxy fault. Every row that rests on one says so.

## 5. Evidence behind the matrix

Every validated `rmw_cerulion` execution used ROS 2 Jazzy: a `ros:jazzy` container on an x86-64 Linux desktop and on an aarch64 Jetson-class machine, a hosted amd64 CI runner, arm64 Docker on an Apple Silicon workstation, and a native RoboStack Jazzy environment on that workstation. No other distro has run ROS 2 nodes over it on hardware or in the full end-to-end sense; Foxy, Galactic, Humble and Lyrical build against those distros' real headers in CI and run the crate's own rmw test suite there, and each per-distro CI check also runs a real rclpy node over `rmw_cerulion` in both directions inside that distro's `ros:<distro>-ros-base` container (an rclpy String talker to a native subscriber, and native Twist and String publishers to an rclpy listener), so all five supported distros exchange messages between a real ROS 2 client and native Cerulion in CI; none of the four is validated on a robot. The one time an `rmw_cerulion` library was loaded under another distro, ROS 2 Foxy, it passed `rmw_init` and then failed at the first typed operation; that library was built for Jazzy, and a build against Foxy's own headers is what the `foxy` lane now runs. The non-Jazzy ROS hosts and containers that appear in benchmark records ran stock RMWs or the DDS bridge, never `rmw_cerulion`.

### What the tree carries for the other distros

- Header probes with gated includes, so bindgen stops aborting on Foxy and Humble headers; capability cfgs; per-era struct size pins; and a load-time refusal when the library and the running distro disagree. None of it changes the Jazzy path.
- Foxy, Galactic, Humble and Lyrical each build against their own real headers in a CI lane, run the rmw suite there, and then run a real rclpy node over `rmw_cerulion` in both directions inside that distro's `ros:<distro>-ros-base` container. Each lane also audits the built library's symbol table, so a build never exports an entry point its distro's headers do not declare. Iron and Kilted have no lane: their arms exist and have never been compiled against those distros' headers.
