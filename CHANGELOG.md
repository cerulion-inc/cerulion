# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

Semantic Versioning in 1.x covers the graph YAML format, the `cerulion` command line and the node macros of `cerulion_macros`. The lower-level Rust API of `cerulion_core` is not covered by SemVer yet, and neither are the library crates behind the command line and the daemons (`cerulion_cli_engine`, `cerulion_wsd`, `cerulion_netd` and `cerulion_bagd`) or the bag library `cerulion_bag`. This release changes public items in each of them, so Rust code that calls them directly may need edits. Prebuilt node cdylibs are a separate matter: every one must be rebuilt for node ABI 28 (see Changed).

### Added
- `tls/<host>:<port>` is a carrier: TLS 1.3 over TCP, for a path where UDP does not get through. It reads the same `tls:` files as `quic/` (`certificate` and `private_key` for a listener, `root_ca` for a connect) and graph-load validation applies the same file rules to it.
- `cerulion_core::NetworkConfig` gains `auth: Option<NetworkAuth>`. `TeamAuth::new` checks a machine key, its team leaf certificate and the team's anchors (`TeamAnchors`: the current issuing CA, retired CAs and, during a rotation, the next or the previous generation's CA) with the `cerulion_pairing::team` profile. A machine opens up to three team sessions on separate listeners, each on `quic/` and `tls/` only, with both ends presenting and verifying a certificate, the keys passed to zenoh in memory and never as files, scouted and gossip-learned peers never dialed in any mode, and a generated zenoh access policy that denies by default and is keyed on the peer certificate's common name. `NetworkAuth::Team` is the data session: a listener accepts only leaves the current issuing CA signed, and the policy admits only current-generation names. A viewer or ci leaf receives data and may query; an operator leaf may also put and answer queries; an owner or robot leaf may send every message. `NetworkAuth::TeamCrossGeneration` carries data with the other live generation during a rotation: it trusts only that generation's CA and admits only that generation's names, so a leaf the next generation's CA signs with a current-generation name fails the data session and is denied every message on the cross session. `NetworkAuth::TeamBundleLane` trusts the retired CAs and the other live generation's CA and admits only the bundle exchange on `cerulion_auth/bundle`, so a leaf a retired CA signs never reaches a data, demand, announce or query key, whatever name it carries; it can still answer a bundle query, whose reply a consumer must check with `cerulion_pairing::team::verify_team_trust_bundle`; nothing in the command line or the daemons consumes a bundle reply yet. zenoh matches the common name, not its issuer, so a live CA's key can issue any name of its own generation. A dialer also trusts the public Web PKI roots, which zenoh's TLS and QUIC clients always load: a listener whose certificate chains there links, matches no team name and is denied every message, so such a dial stays up and carries nothing. A `tcp/` or `udp/` locator, a datagram-only `quic/...?rel=0` locator, a locator with a `#` endpoint config, or certificate files set beside team credentials fails the session open naming it. Nothing in the command line or the daemons sets `auth` yet, and `graph run` refuses to hand it to a gateway child. `cerulion_core::transport::test_ca` (feature `test-helpers`) issues test team credentials in memory.
- `cerulion topic type <TOPIC>`, `cerulion topic find <TYPE>`, `cerulion topic bw <TOPIC> [--window N]` and `cerulion topic list -t` (also `--show-types`), the counterparts of `ros2 topic type`, `find`, `bw` and `list -t`. `topic type` prints a topic's `package/Type`, local or remote, read from one message. `topic find` takes `package/Type`, `package/msg/Type` or a bare workspace `Type` and lists the local topics of that type and the remote ones whose robot catalog names it (`--local` reads local topics only). `topic list -t` prints each row's type after the topic name, LOCAL rows from one message within one shared one second wait and REMOTE rows from the robots' catalogs, with `[unknown]` where the type is not known; plain `topic list` output does not change. `topic bw` prints once a second the payload bytes per second over the newest `N` messages (default 100, from 2 to 100000), in decimal units, measured from the messages' wire stamps.
- A graph's `network:` block can choose QUIC for the cross-host link. The carrier is the locator's first segment: `quic/<host>:<port>` is QUIC over TLS 1.3 with one stream per priority, `quic/<host>:<port>?mixed_rel=1` adds a datagram link on the same connection and port, and `udp/<host>:<port>?rel=1;mixed_rel=1` is QUIC with no encryption and no peer authentication, for a WireGuard overlay that supplies both. TCP stays the default. A new `tls:` block names the PEM files (`certificate` and `private_key` for a `quic/` listener, `root_ca` for a `quic/` connect, which also checks that the certificate names the host or IP it dials); a self-signed certificate can be its own `root_ca` when it is not marked `CA:TRUE`, and a `quic/` listener whose certificate is marked `CA:TRUE` refuses to start, naming the file and the `openssl` flag that mints an end entity. `cerulion-netd` reads the same files from `CERULION_NETD_TLS_ROOT_CA`, `CERULION_NETD_TLS_CERTIFICATE` and `CERULION_NETD_TLS_PRIVATE_KEY`.
- `CERULION_UNENCRYPTED_QUIC=on` (opt-in, read by `cerulion-netd`) listens on zenoh's unencrypted QUIC carrier, `udp/<host>:<port>?rel=1`, beside every `tcp/` listen locator on the same port, advertises it in the mDNS record as `udp_rel=<port>`, and dials it first: at start-up netd checks each discovered peer that advertises it, and each `CERULION_NETD_CONNECT` locator written that way, over UDP, and dials it over QUIC when it answers or over `tcp/` on the same port when it does not, with one warning that starts `QUIC FALLBACK:` and names the locators and the reason. The check waits at most `CERULION_NETD_QUIC_PROBE_TIMEOUT_MS` (default 1000, at most 6000). Explicit `tcp/` locators are used as written. This QUIC has no encryption and no peer authentication, the same as `tcp/`. What it changes is congestion control: a Linux TCP connection that idles longer than one retransmission timeout restarts from its initial window, while the QUIC stack has no idle reset, so a large message sent about once a second does not pay the extra round trips. With the setting unset, nothing changes.
- A graph's `network:` block takes `default_reliability: reliable | best_effort` (default `reliable`), the put reliability of every `egress` entry that sets no `reliability` of its own. An entry's own `reliability` wins in both directions, and an entry may set `reliability: reliable`, so one topic can stay reliable under a `best_effort` default. Graph-load validation refuses a `best_effort` default on a graph with no `mixed_rel=1` locator, as it refuses a best-effort topic, and an unknown value is a parse error naming it. The receive path is unchanged.
- An `egress:` entry can be a map, `{topic: /r/scan, reliability: best_effort}`, beside the bare topic name it was. A best-effort topic is put with zenoh's best-effort marker and rides the QUIC datagram link of a `mixed_rel=1` connection, so a lost frame is not retransmitted and later frames are not held behind it; every other topic is put at the block's `default_reliability`. Graph-load validation refuses a best-effort topic on a graph with no `mixed_rel=1` locator, a `quic/` locator without the certificate files it needs, a `tls:` file no `quic/` locator reads, and a locator whose carrier this build does not compile (`ws/`).
- One message file types a port in both languages. A workspace's `schemas/<pkg>/msg/*.msg` files and `schemas/*.yaml` schemas generate into the Rust message crate beside the built-ins (`native_ros2_messages::<pkg>::<Type>`, a package-less YAML schema at the crate root) and into the Python `cerulion.msgs` namespace (`from cerulion.msgs.<pkg> import <Type>`), by the one resolution rule the runtime uses, so the type, its layout and its wire hash agree. `workspace create` and `workspace init` set `CERULION_WORKSPACE_MSGS` in `.cargo/config.toml`; an existing workspace adds `CERULION_WORKSPACE_MSGS = { value = ".", relative = true }` under `[env]`. `node create` and `node modify` now scaffold a Rust port of a `.msg` store type, which they used to refuse; in a workspace without the setting it is refused with the line to add.
- Python message classes: every message is a class in `cerulion.msgs` (`from cerulion.msgs.sensor_msgs import LaserScan`), and every view of a schema is an instance of its class, nested fields included. The wheel ships type stubs for the built-in packages; `cerulion node build` writes a workspace's stubs to `.cerulion/python/cerulion-stubs/`, as does `python -m cerulion.msgs`. `SchemaSet.message_type(name)` returns the class of any schema set.
- `cerulion graph pause <RUN>` and `cerulion graph resume <RUN>` hold a live run at its next step boundary and stop its clock, so timers neither skip ticks nor burst on resume and a recording shows no gap across the pause. A run's `run.json` records `"paused"`, and the viz daemon's `runs` rows carry `"paused": true` while a run is held. A run that is never paused is unchanged.
- `cerulion bag play <BAG> --resim all --record-out <PATH>` writes the frames the re-executed graph published to a new bag: one channel per graph-produced topic, labelled with the schema the re-executed graph publishes, with its name and provisioning copied from the input bag's channel where it has one. It works with and without `--verify`. The path must not exist, so an existing file is refused with exit 2 and never overwritten, and a run that does not finish removes the partial file. The `--report` JSON gains a `record_out` field naming the written path; reports from runs without the flag are unchanged, and `report_version` is unchanged.
- `cerulion-wsd` creates and builds. `graph.create`, `node.create` and `schema.create` do what `cerulion graph create`, `node create` and `schema create` do and answer with the `version` of the file they wrote, which a graph or node edit can send as `expect_version`. `node.build` runs `cerulion node build` and streams cargo's compiler messages as structured `diagnostic` events (file, line, column, level, message, code), then a `done` event; a client that closes its connection cancels the build. The protocol version is unchanged: an older daemon answers the new verbs with `unknown_verb`, and every existing verb is as it was. `cerulion_cli_engine` gains `node_cmd::node_build_streaming`, and `node create`'s trigger-policy defaulting moved from the `cerulion` binary into `node_cmd::resolve_create_policy` so the daemon applies the same rules.
- `cerulion-vizd` answers a new `sample` request: the newest 1 to 20 messages of an attached topic, each as `seq`, `ts_ns`, `size`, the decoded `fields` where the schema is known (or `null`) and a one line `summary`. The daemon keeps frames only for a topic that is being sampled, drops the ring five seconds after the last request, keeps at most eight rings, and keeps no body larger than 16 KiB, so sampling adds no subscription and a bounded amount of memory. The control protocol version in the banner is unchanged; a daemon without the verb answers it with the structured unknown-method error. See `docs/user-api.md`.
- `cerulion-remoted`, the robot-side remote-access daemon, ships in every release archive, in the Debian package (`/usr/bin/cerulion-remoted`) and in the Homebrew formula. `install.sh` places it beside the CLI and links it with the other programs (see the install script entry under Changed); a v1.0.0 archive, which does not carry it, still installs, and removes a `cerulion-remoted` a later release left in the install directory along with its link. `--uninstall` removes it.
- `cerulion-wsd` can wire and unwire a graph and remove a node from it. `graph.wire` and `graph.unwire` add or delete one `inputs:` entry, and `graph.unstage` deletes a node entry. Each takes an optional `expect_version`, edits the file in place so comments and layout survive, and refuses a wire between different schemas (`schema_mismatch`) or removing a node other nodes read from (`would_break`, with the wires listed) unless `force` is set. The protocol version is unchanged.
- `install.sh --uninstall` (`curl ... | sh -s -- --uninstall`) removes what the script installed: the programs and libraries, the links that point at them and, when the env file names that install, the marked line in each shell startup file and the env files. A directory without the installer's marker is left alone. The sign-in, keys and settings in `~/.cerulion` and the Rust toolchain stay.
- A Python client, new in this release: `import cerulion` publishes and subscribes to topics on the local machine over the same shared memory as Rust nodes, with no copy on receive. Call `cerulion.connect()`, then `session.publisher(topic, schema=T)` and `session.subscriber(topic, schema=T)`. `subscriber.receive(timeout_ms)` returns a `Frame` whose `view()` reads fields in place, `with publisher.loan(...) as msg:` writes straight into the outgoing slot, and `cerulion.open_bag(path)` reads a finished `bag record` bag. Cross-host topics are not exposed yet. Build it from source with `cd crates/cerulion_py && maturin develop --release` (Python 3.11 or later); the release archives do not carry a wheel.
- Nodes can be written in Python. `cerulion node create <TYPE> --lang python` writes `nodes/<TYPE>/node.py`, a class decorated with `@cerulion.node(...)` whose ports are `cerulion.input(T)` and `cerulion.output(T)`, plus a cdylib that embeds CPython. `graph run`, recording and replay treat it like a Rust node. A Python node must declare `period_ms`, one `trigger=True` input or `sync_window_ms`; `--raw-ffi` and `node modify` refuse it. `node build` uses `CERULION_PYTHON`, else `<workspace>/.venv/bin/python`, else `python3`. `cerulion node new` is now an alias of `node create`.
- Python APIs take message classes. `cerulion.input(T)` and `cerulion.output(T)`, `session.publisher(topic, schema=T)`, `session.subscriber(topic, schema=T)`, `frame.view(T)` and `record.view(T)` take a class from `cerulion.msgs`; a quoted schema name is accepted with `schemas=` (and alone in a node port) for a schema with no class. `Frame.view` and `Record.view` take the schema first; a call that passes the schema set first is refused with a `TypeError` that names the replacement spellings, `view(LaserScan)` and `view('pkg/Name', schemas=schemas)`. A class used against a set that resolves its name to another hash raises `SchemaMismatch`. The `node create --lang python` scaffold writes `import cerulion` and typed imports.
- Node parameters: mark a plain field of a `#[cerulion_node]` struct with `#[param(default = .., min = .., max = .., description = "..")]` to make it a typed setting (`bool`, `i8` to `i64`, `u8` to `u64`, `f32`, `f64` or `String`). A graph sets it per node with a `params:` map on the node entry, for example `params: {gain: 0.5}`. Values are checked for type and bounds when the graph loads and are written into the field before `init`. `graph validate` prints a `params '<node id>'` line per node, and `node info` prints a `Params:` table. A recording keeps the values, and `bag play --resim` applies them.
- Launch arguments: a graph declares a top-level `args:` map. Each entry is a default (`side: left`) or `{default: .., description: ..}`, and it is used as `${name}` in `prefix`, an output's `topic`, an input's `source` and `params:` values (`$$` is a literal `$`). `cerulion graph run <NAME> side:=right gain:=0.5` overrides values for one run. A name the graph does not declare is refused with the nearest declared one, and a word without `:=` is a usage error. A graph with no `args:` loads exactly as before, and a recording stores the resolved graph.
- `#[input(accumulate)]` on a node input hands each fire every frame that arrived since the node's last fire, not only the newest. Frames come oldest first by publish time; read them with `self.<input>.iter()`, `len()` and `is_empty()`. `cap = N` (default 10, range 1 to 64) bounds what one fire holds; past it the oldest frames are dropped and counted in `dropped()`. An accumulate input never fires the node. It cannot be combined with `trigger`, `depth`, `backpressure = block` or `backpressure = sample(N)`.
- Generated message types keep a `.msg` file's constants and field defaults. `int8 STATUS_FIX=0` becomes `NavSatStatus::STATUS_FIX`, and `float64 w 1` or `int32[] ids [1, 2]` set the value that `Default` builds. Neither changes the wire layout or the schema hash, and a loaned output slot still starts zeroed. A constant or default that does not fit its type, or a constant whose name is not upper case, is a parse error naming the line. `cerulion_core::codegen` also reads `.srv` files (`parse_rossrv`, `split_rossrv`) into `<Name>_Request` and `<Name>_Response` messages.
- `cerulion_core::dynamic` converts any message to YAML and back using only its schema: `message_to_yaml`, `message_to_yaml_with` and `yaml_to_message`. Reading YAML enforces ROS 2 `string<=N` and `T[<=N]` bounds and names the field path in errors. A block copied from `topic echo` output reads back to the same message.
- `cerulion logout` signs this machine out: it removes the session and refresh tokens from `~/.cerulion/auth.json` (the account id stays) and then revokes the session at the account service. Every command that needs an account then starts a sign-in at a terminal, and is refused with exit 7 elsewhere (a script, a CI job), until the next `cerulion login`. It prints one line, `signed_out: account=<id>` or `not_signed_in`, and exits 1 if the file could not be rewritten or the service did not confirm the revoke.
- `cerulion workspace create <NAME> --starter obstacle_avoidance` creates a complete workspace from sources bundled with this CLI version: a laser scanner node and a safety controller node with their tests, and the `obstacle_avoidance` graph. `starter.toml` records the CLI version and compiler. Creation is atomic and refuses any existing path; on a filesystem without a no-replace rename (some network, FUSE, SMB or FAT volumes) it is refused with the reason.
- `--local` keeps a command on this machine. On `graph run` and `node run` it is the same as `--network off`. On `topic list` (where `--no-network` is an alias), `topic echo`, `topic hz` and `topic info` it skips remote discovery, the robot schema query and starting `cerulion-netd`, reading only publishers on this machine. On `topic echo`, `hz` and `info` it also refuses a topic that `cerulion-netd` or `cerulion connect` re-injected from a robot. `CERULION_NETWORK=off` still selects the same scope.
- `graph run`, `node run` and `ros2 attach` log one line when the run sends topics off the machine over `tcp/` from a Linux host whose `net.ipv4.tcp_slow_start_after_idle` is nonzero, the Linux default: a warning naming the locators when a per-run gateway's locators include `tcp/`, and an info line when the egress goes through the shared `cerulion-netd` session, which every networked run registers with whether or not a remote peer subscribes. On such a host the congestion window of an idle TCP connection decays toward its initial size, so each large message sent at a low rate pays a few extra round trips, a cost that grows with the path's round-trip time; measured over a 31 ms wide-area path, a 301 KB message once per second took 164.8 ms p50 on `tcp/` and 79.3 ms on `quic/`. The line names both fixes: the sysctl set to 0 on the sending host, or `quic/` on both ends. A run with no egress, a gateway with no `tcp/` locator, and any other host log nothing.
- Usage telemetry. The `cerulion` CLI sends usage telemetry, on by default, when the build carries a telemetry key; `cerulion telemetry status` says whether this build has one. A source build carries none, `POSTHOG_API_KEY` supplies one to any build, and `POSTHOG_HOST` changes the destination (https only). The first command that could send prints a notice on stderr and sends nothing; later commands send. To turn it off, use `cerulion telemetry off` (saved in `${CERULION_HOME:-~/.cerulion}/telemetry.json`), `DO_NOT_TRACK=1` (or `true`) or `CERULION_TELEMETRY=0`; `DO_NOT_TRACK` wins over `CERULION_TELEMETRY`, which wins over the file. `cerulion telemetry status` names the deciding setting, `cerulion telemetry on` turns it back on, and the verb needs no sign-in. See `docs/telemetry.md`.
- What the telemetry sends: one `cli_command_run` per command (`verb`, `subverb`, `exit_code`, `duration_bucket`, and `install_method` of `install.sh`, `deb` or `brew`, read from a marker the installer leaves: `.cerulion-provenance.json` beside the programs, or `share/cerulion/install.json` for the package and formula). Also `graph_run_started`/`graph_run_completed`, `node_build_completed`, `bag_record_completed`/`bag_record_failed`, `bag_replay_completed`, `resim_completed`, `ros2_bridge_started`, `connect_session_completed`, `pair_completed` and `cli_login_completed`, which carry only flags, counts, exit codes and size or duration buckets. Every event also carries `surface`, `env` (`prod` or `dev`) and `app_version`. Never sent: arguments, paths, names, URLs, emails or message contents; a value that looks like one, or is over 128 characters, is dropped. Events go to PostHog in one batch at exit, waiting at most 300 ms; on a slow network they are dropped, never stored. `telemetry`, `completions`, `bagd` and internal subprocesses send nothing.
- CLI telemetry events carry your Cerulion account id once the machine has signed in to a hosted account, and otherwise a random `anon:<uuid>` kept in `telemetry.json`; `cerulion-vizd` events always carry the random id. A machine's first `cerulion login` sends that random id with the sign-in request so earlier events join the account, and the CLI sends PostHog one alias event that links the two ids. A different account signing in replaces it, and deleting `telemetry.json` resets the id and the notice. `cerulion-vizd` sends `vizd_started` (`os`, `arch`) and a `vizd_heartbeat` (`uptime_minutes`) every 15 minutes under the same consent settings, and only when `POSTHOG_API_KEY` is set in its environment; a running daemon checks consent again before each heartbeat.
- `cerulion graph levels` ends with a chains block: the trigger edges that could run as one fused chain inside one process, and for every other consumer edge the reason it stays queued (`fan-out`, `separate-processes`, `opted-out` and others). Each `graph run` writes its own census under `chains` in `run.json`. A node entry may declare `fuse: false` to end a chain at that node. Nothing in the runtime fuses chains yet, so runs are unchanged.
- `cerulion bag play <BAG> --resim all` resumes a free-run bag that begins mid-run, such as a Flashback capture, when the recording holds one worker process. It restores from that bag's checkpoint and periodic firing deadlines. A mid-run free-run bag with several worker processes is still refused with exit 2; the message names the worker count and says to re-execute the bag from its start or capture a graph that runs in one process group.
- `cerulion_core` gains an opt-in `local-transport` Cargo feature for an app whose publishers, subscribers and gateway all run in one process, such as an Android app that cannot use cross-process shared memory. Publish and receive stay zero-copy inside the process, and a gateway still serves topics over TCP. With the feature on, `process_groups:`, cross-process initialization and native cdylib nodes are refused. See `docs/android.md`.
- Cerulion builds and runs on Android, API 30 or newer, arm64-v8a and x86_64, cross-built with cargo-ndk. That covers shared memory publish and subscribe between processes, and `cerulion graph run`, `topic`, `bag` and `cerulion-netd` from `adb shell`, with node libraries cross-built on a host. `crates/cerulion_android` embeds the runtime in an app. An Android gateway announces itself over mDNS and refuses LAN topic requests by default: `CERULION_LAN_ACCESS=open` (or the app's `lan_access` key) serves them, and other platforms default to `open`. See `docs/android.md`.
- `rmw_cerulion` builds from source and runs on ROS 2 Foxy, Galactic, Humble and Lyrical as well as Jazzy. CI builds it against each distro's own headers, runs its test suite and exchanges messages with a real rclpy node in both directions; a manually started emulated arm64 Foxy job builds it and runs the rclpy exchange. Iron, Kilted and Rolling are not built or tested, and the release packages carry the Jazzy library only. On Foxy and Galactic, a C++ (rclcpp) message with a `bool[]` member can be neither published nor received: each one is refused, naming the member.
- An `rmw_cerulion` library built for Kilted, Lyrical or Rolling refuses to load, at `rmw_init` and the init-options calls, in a process that sets no `ROS_DISTRO`, because those distros lay out their structs differently from Jazzy and earlier. The error names the distro it was built for and the setup file to source (`source /opt/ros/<distro>/setup.bash`, or both files for the Lyrical and Rolling pair). A library built for Jazzy or earlier loads as before.
- On ROS 2 Lyrical, `rmw_cerulion` publishes a message whose `rosidl::Buffer` field lives on a non-CPU backend (for example `cuda`, as in GPU camera pipelines) by copying it to host memory. Each topic logs a warning on its first copy and at every power of ten. A subscription whose `acceptable_buffer_backends` names a backend the rmw lacks is created with one warning and receives CPU data; only a malformed list fails.
- `cerulion-vizd` can load a robot's URDF model onto an attached `unitree_go/LowState` topic through two new control socket requests: `load_model` (`urdf_path`, `topic`, `model_id`, and 1 to 12 `motor_joints` in motor-array order) and `model_status`. The model is checked before any mesh file is read (fixed, revolute and continuous joints, one GLB, OBJ, STL or DAE mesh per link, at most 16 MiB of XML), its meshes are read within a 256 MiB budget, and it is then drawn at `models/<model_id>` with its joints driven by the measured motor angles. See `docs/user-api.md`.
- `cerulion-vizd` draws voxel-delta map streams. A `sensor_msgs/PointCloud2` whose fields are exactly `vx_<N>mm`, `vy_<N>mm`, `vz_<N>mm` (`int16`), `hits` and `op` (`uint8`), with `point_step` 8, is read as map edits rather than points. The viewer keeps the map under the topic as static tiles of height-coloured cubes, walls, outlines and the robot's trail. `attach`, `status` and `list` report such a topic as `VoxelMap`, where they reported `Points3D`.
- `cerulion-rcpd` is an MCP server that lets an agent read a running graph (`robot://graph`, `robot://state/{name}`) and call only the tools an `rcp.yaml` manifest declares, plus a built-in `estop`. Arguments are checked against each tool's `input_schema` before anything is published. Every call goes into a hash-chained receipt log (`--verify-receipts <log>` checks it), and every call that passes the checks is published on the manifest's `journal.calls_topic` (default `/rcp/calls`), so a recording replays with `bag play --resim all --verify`. `--http` needs `CERULION_RCP_TOKEN`. It is not in the release archives; build it with `cargo build --release -p cerulion_rcpd`. See `docs/rcp.md`.
- `cerulion_cli_engine::bag_cmd::PlaySummary` gains `scheduled_advance_ns`, how long a played bag should have taken measured from its first frame: the longest played channel's scheduled advance at the given `--rate`, with none of the wall time spent before the first frame. `scheduled_span_ns` is unchanged and equals the run origin plus this value.

### Fixed
- `cerulion bag play --resim` on a free-run bag no longer stands down the read-log-steered injection on a consumer whose recorded step took more frames than its input's declared depth (frames that arrived while it fired, pulled by the refill between fires). It used to report `queue_overflow` and fall back to the recorded-clock window, which could evict frames the recording delivered, hand the consumer nothing for several fires, and leave its reads off by the evicted frames. The replay now builds that input's queue as deep as the recorded schedule fills it, logs one line per raised input naming both depths, and reproduces the recorded reads. `queue_overflow` remains for a live producer's own connection over its depth and for a schedule deeper than replay will provision (16 frames on a `multi_publisher_topics` topic, the shared ceiling; 64 on any other, the deepest an input may declare). `cerulion_core` gains `GraphRuntime::build_with_schema_hashes_and_wiring` and `CrossProcessWiring::with_input_depth_floors`; in `cerulion_cli_engine::replay_inject`, `ConsumerEdge` gains `provisionable_depth` and `InjectionSchedule` gains `depth_raises` (`DepthRaise`).
- A reliable egress topic is no longer dropped at the sender when the network link is congested. zenoh's default put discards a frame when its transmit queue stays full and still reports success, so the gateway counted such a frame as forwarded. Reliable topics now wait for the queue instead, for up to zenoh's `wait_before_close` (5 s by default), after which zenoh closes the link to that peer. Each egress topic has its own bounded send queue and sender thread, so a congested link holds up only the topics it carries, not the gateway's other links (closing LAN access waits for a put already under way). When a reliable topic's send queue is full the new frame is refused, counted, and a warning names the topic; a best-effort topic drops its oldest queued frame instead. An egress entry's new `send_queue: N` sets the bound, which otherwise is the depth of the gateway's tap on the topic. Every gateway logs every 10 s a warning for a topic that refused or failed frames (an info line for best-effort drops), and each topic's totals when it stops; the `cerulion-netd` gateway also reports the counters in its `status` reply.
- On ROS 2 Lyrical, `rmw_cerulion` exports `rmw_get_clients_info_by_service` and `rmw_get_servers_info_by_service`, which report `RMW_RET_UNSUPPORTED`; `rmw_implementation` used to print a failed-to-resolve warning for each at startup. Builds for Jazzy and older distros, whose headers do not declare the two calls, still do not export them.
- `cerulion-vizd` refuses a remote `attach` that pins a different `schema` than the topic's live remote tap was attached with, and names both schemas in the error. It used to answer `ok` with the new schema name while the mirror kept carrying the original type, and once a frame had decoded the reply paired that name with the frames' archetype while `status` and `list` kept the original schema. Detach the topic first to attach it with a different schema.
- iceoryx2 node ids no longer depend on uninitialized shared memory: the shared counter that goes into every node id now starts at zero when its segment is created, where it used to start from whatever bytes the new segment held.
- A graph with a `network:` block can send a topic that a process outside the graph publishes on the same machine, such as a ROS 2 program running on `rmw_cerulion`. List it under `egress:` as `{topic: /chatter, external: true}`: the gateway announces it, and a remote that demands it receives its frames. Before, graph-load validation refused any egress topic no node in the graph produced, and an unlisted outside topic was announced but refused at the bridge, so a remote subscriber found it and received nothing. Topics the block does not list still never leave the machine. `external: true` on a topic a node in the graph produces is refused at graph load, and the refusal of an unmarked entry with no producer now names the `external: true` spelling.
- `CERULION_NETD_NETWORK=off` now keeps `topic list`, `topic echo`, `topic hz`, `topic info` and `schema info` local, as `CERULION_NETWORK=off` does: they open no zenoh discovery session, run no discovery ladder, and neither query nor start `cerulion-netd`. Before, `topic list` scouted the LAN under it, and a remote schema lookup that netd answered "not network-configured" fell back to a scouting session of its own. Only the exact value `off` engages it, as in the daemon, and a refusal names the variable that engaged it. `cerulion viz --robot` now refuses when `CERULION_NETWORK` is `off` or holds a value it cannot read, or when `CERULION_NETD_NETWORK=off` or `CERULION_VIZD_NETWORK=off` is set, before it spawns or contacts the daemon, and `cerulion pair` refuses under `CERULION_NETWORK` before its mDNS lookup and before it spawns `cerulion-connectd`.
- The discovery peer cache honours `CERULION_HOME`: `cerulion topic list` and `cerulion-netd` read and write `$CERULION_HOME/peers.json` when it is set, as documented, where they used to use `~/.cerulion/peers.json` regardless. `cerulion_discovery::peer_cache` gains `cache_path_from`.
- Under `rmw_cerulion`, a third ROS 2 node on one machine could not start: every node publishes `/rosout`, the topic's shared memory service held two publishers, and `rcl_node_init` failed on the third node's `/rosout` publisher (in practice the `ros2` daemon's). A topic that an rmw publisher or subscription creates now holds 32 publishers, up from 2, and up to 32 subscriptions, up from 8: 1 GiB divided by the type's slice ceiling, at most 32, so a 128 MiB tier type (`sensor_msgs/Image`, `PointCloud2`, unlisted variable-size types) keeps 8 and one publisher still reserves about 18 GiB of virtual address space. On an arm64 kernel with 39-bit addresses, lower a large type's ceiling with `CERULION_RMW_SLICE_CEILING`, for example `sensor_msgs/Image:8388608`. Such a topic admits one process per publisher and subscriber slot (64 for most types, 40 for a 128 MiB tier type) where iceoryx2's default is 20, and its event ports follow its data limits even when `iceoryx2.toml` raises them. A topic another process created first keeps the slots it was created with, and an rmw endpoint still attaches to it.
- Under `rmw_cerulion`, `ros2 node list` failed with "Failed to get node names: error not set". rcl hands `rmw_get_node_names` arrays with no allocator set, and the rmw returned `RMW_RET_BAD_ALLOC` instead of filling them with the default allocator. `rmw_get_node_names_with_enclaves` had the same defect and is fixed too.
- `cerulion node create` refuses two outputs of one name, and (outside `--raw-ffi`) an output named like an input, with a validation error. Both used to scaffold a node whose source could not build.
- A graph could die with no panic text when the `cerulion` host and a node cdylib had been built against different layouts of a transport type. A type whose field types change is re-packed by the compiler, which can leave its size, its alignment and its field names identical and still move its fields, so a node built earlier reads a field at an offset the host no longer writes. The fix is one of the changes behind this release's new node cdylib ABI, so every prebuilt node cdylib must be rebuilt (see the node ABI entry under Changed).
- The lockfiles move tokio to 1.53.3, which fixes RUSTSEC-2026-0386 (`AsyncFd` constructors that violate I/O safety), and ctutils to 0.4.4, which fixes RUSTSEC-2026-0385 (non-constant-time mask generation and `u128` comparisons). The `aspire_arm` example, new in this release, uses tokio 1.54.1, which fixes RUSTSEC-2026-0384.
- A Flashback capture of a free-run multi-process `graph run` started without `--record` can be re-executed with `cerulion bag play --resim`. Before, only `--record` put the workers on the clock that replay needs, so replay refused a plain run's trace at its first message.
- Each Cerulion process that builds a transport raises its soft open-file limit at start: to the hard limit on Linux (at most 1048576), and at most to 1024 elsewhere. On Linux, under the usual 1024 soft limit, a graph of about 40 nodes no longer fails to start with `UnableToCreatePortTag`. `rmw_cerulion` and Python's `cerulion.connect()` raise it at most to 1024. `graph run` and `graph profile` refuse a graph estimated to need more (40 plus 14 per output port and 22 per input port), naming the fix; `CERULION_OPEN_FILE_CHECK=0` starts it anyway with a warning.
- Nested fields decode against the right definition in a workspace that defines a type twice: once as a packaged schema and once as a package-less YAML schema whose name is written `pkg/Type`. This applies to `topic echo`, `schema info`, the viz daemon and header stamp capture, and each definition stays reachable by its own schema hash. Before, a nested field could bind to the other definition or fail to resolve. A reference that does not bind now returns a typed error from the new `try_layout_of` (`LayoutError::UnresolvedNested`), as the frame walker's `WalkError::NestedResolutionFailed` already did.
- `cerulion clean` and `cerulion clean --report-only` run on a machine that has never signed in (they read no account and reach no network), so a CI runner or a fresh install can clear what a killed process left behind. `cerulion clean --report-only` deletes nothing: it lists the dead-node entries a plain `cerulion clean` would remove (ten, then "and N more") and ends with "Report only: nothing was removed." and the command that acts on the list. Before, the dead-node sweep ran before the flag was read.
- A URDF with a malformed number no longer loads with a limb drawn at the origin. Every `origin xyz`, `origin rpy`, `axis xyz` and mesh `scale` it supplies must be three finite numbers, where a bad value used to be read as zero; otherwise the model fails to load with an error naming the element, attribute, line and text. An absent attribute keeps its default. A configured motor joint that is not revolute or continuous is left still, with a warning naming it.
- A camera topic's decoded picture is placed under the topic's frame in the viewer, where it was drawn at the world origin. The viz daemon's render queue holds 128 batches (it held 8) and takes in its backlog before each render, so two 500 Hz topics no longer drop whole batches and blank the camera pane until the next keyframe. The `status` worker block reports `absorbed_batches`.
- A world-frame map cloud shows only its latest frame in the viewer, where the last eight frames were drawn over each other and every wall looked a voxel thick. A topic counts as a map when its name contains `world_cloud`, `cloud_world`, `map/cloud` or `cloud_map` (any case); other point clouds keep accumulating sweeps. A map topic stays in the world frame under a loaded URDF and is not mounted on the lidar link.
- The lockfiles move rustls from 0.23.45 to 0.23.46, which fixes RUSTSEC-2026-0346 to RUSTSEC-2026-0349 (TLS secrets in Debug output, a 1 GiB certificate decompression before authentication, and two handshake defects). rustls-webpki moves from 0.103.15 to 0.103.16, which fixes RUSTSEC-2026-0382 (distrusted intermediates accepted). webpki-roots and webpki-root-certs move from 1.0.9 to 1.0.10, which fixes RUSTSEC-2026-0381 and RUSTSEC-2026-0383.

### Changed
- Usage telemetry is quieter and says more about itself. The first-run notice is one line, printed only when stderr is a terminal; a command without a terminal prints no notice and sends as usual. A CI run (`CI`, `GITHUB_ACTIONS` and the other variables listed in `docs/telemetry.md`) prints no notice, sends with `ci: true` and no person profile under a random id minted for that process and never stored, so no later login can join it to an account; every event now carries `ci`. `CERULION_TELEMETRY` also accepts `false`, `off` and `no`, in either case, to turn telemetry off. `cerulion-vizd` sends nothing until the CLI has shown the notice on the machine, except under CI. `docs/telemetry.md` now lists the fields PostHog adds, the `$create_alias` event, that events are sent as they are queued, the PostHog host, the IP address and the location derived from it, and how long events are kept. `cerulion_telemetry::Common` gains a `ci` field.
- `CerulionRuntime` (the `cerulion_android` Java facade) no longer loads `libcerulion_android.so` by itself. Call `CerulionRuntime.loadLibrary("<library name>")` once before any other method, with the name of the app's runtime library. Every other method throws `IllegalStateException` until then, and a second `loadLibrary` with a different name throws `IllegalStateException`.
- `cerulion node create` writes node crates with `crate-type = ["cdylib", "rlib"]` and a `pub` node struct, so another crate, such as an app's own native library, can link a node as a plain dependency with `default-features = false` (which compiles the node's C exports out) and name it by its `<Struct>Entry`. The cdylib that `cerulion node build` and `cerulion graph run` load is unchanged. The `obstacle_avoidance` starter and example and the `basic_timer` example use the same layout. An existing node crate links this way after two edits: add `"rlib"` to its `crate-type` and make its `#[cerulion_node]` struct `pub` (see `docs/user-api.md`).
- `cerulion_android` builds as a Rust library only (`crate-type = ["rlib"]`); it no longer produces `libcerulion_android.so`. An app links it into its own runtime crate, a `cdylib` that also links the app's graph nodes, and ships that one library: copy `target/<triple>/release/lib<runtime>.so` into `jniLibs/<abi>/` rather than using `cargo ndk -o`, which also copies each node crate's own library. `tools/scripts/android_jnilibs_gate.sh` checks a jniLibs tree for exactly one library per ABI, built for that ABI, 16 KB aligned `LOAD` segments, `JNI_OnLoad` and no node exports. The sample app now ships its graph (`timer`, `relay`, `printer`) as an APK asset, links those nodes into `libcerulion_sample_runtime.so` from `crates/cerulion_android/android/runtime`, and the emulator test checks their topics, recordings, a restart in the same process and a start after a kill. An app that loaded `libcerulion_android.so` makes a runtime crate (see `docs/android.md`, `App embedding`) and passes its name to `CerulionRuntime.loadLibrary`.
- An Android app can run graph nodes in its embedded runtime. The app's runtime crate links the node crates as plain libraries and lists them once with `cerulion_android::embed_nodes! { "timer" => timer::TimerNodeEntry, ... }`, which defines the library's `JNI_OnLoad` and registers each graph YAML `type:`. A start looks every node up among the linked types and makes fresh nodes, so a stop and a new start in one process run new instances. A type that is not linked, a type listed twice, or `node_lib_dir` with a native-node graph on the in-process transport fails the start with error code 5 and a message that says why. The status JSON gains `linked_nodes`. `cerulion_android` is now published with the workspace, and gains a `local-transport` feature for host builds on the app's transport. See `docs/android.md`, `Graph nodes in an app`.
- `NetworkBlock::egress` (the `network:` block of a `GraphConfig`) holds `EgressTopic` entries where it held `String`s. A 1.0 graph file's list of topic names parses unchanged, and an entry with no `reliability` and no `external: true` serializes back to its bare name. In Rust, `EgressTopic` converts from `&str` and `String` (`vec!["/r/cmd".into()]`), reads back as `&str` through `as_str()` and `AsRef<str>`, formats as its topic name, and compares with `str`, `&str` and `String` in either order, so `block.egress == vec!["/r/cmd"]` holds; a string equals an entry only when the entry sets neither a `reliability` of its own nor `external: true`. The field's type is still new to 1.0 code, which needs these edits: `vec!["/t".into()]` where it wrote `vec!["/t".to_string()]`, `.into()` where it pushed a `String`, `iter().any(|t| *t == s)` where it called `contains(&s)` with a `String` `s`, and `NetworkBlock::egress_topics()` where it needs the names as `&str`s.
- Discovery on a LAN uses mDNS by default, and zenoh multicast scouting is off. Either way only a machine with a listen endpoint can be reached: a robot needs `CERULION_NETD_LISTEN` (for example `tcp/0.0.0.0:7683`) or an enabled `network:` block with a `listen:` entry (which also limits what crosses to the block's `egress` list), and without one its netd has no address to dial and neither mDNS nor multicast scouting finds it. To scout listening peers by multicast as 1.0 did, for a network where mDNS does not cross, set `CERULION_MULTICAST_SCOUTING=on` on both machines, in the environment `cerulion-netd` and `cerulion-vizd` start with (a running daemon keeps its value until it restarts); a robot whose listener comes from a graph `network:` block is not scouted by multicast, so reach it over mDNS or `CERULION_NETD_CONNECT`. In detail: `cerulion-netd`, `cerulion-vizd`, the per-run gateway process and the `topic list` discovery session no longer send scout packets to UDP `224.0.0.224:7446`; gossip scouting stays on. Peers are found over mDNS instead: at boot `cerulion-netd` browses `_cerulion._tcp` for 800 ms (one PTR query per interface) and dials every answering gateway whose address accepts a TCP connect, together with the reachable rows of `peers.json` under `${CERULION_HOME:-~/.cerulion}`, so a desk reaches a listening robot on its LAN with no address configured, and an idle machine sends no discovery traffic after its one mDNS registration. A desk `cerulion-netd` does not listen or advertise unless `CERULION_NETD_LISTEN` is set, so a robot that boots after a running desk is found when the desk's netd next starts (it exits 30 s after its last user), or right away if the robot was listed in `CERULION_NETD_CONNECT` when that netd started (or multicast scouting is on at both ends). A machine's own netd and gateway processes (its identity on one of its own addresses) are left out of its own `topic list` and boot fold; `cerulion_discovery::ladder` gains `drop_this_hosts_gateways` and `drop_this_hosts_gateways_with`. `cerulion_mdns` gains `browse_rung` and `instance_from_fullname`, moved from `cerulion_cli_engine::mdns_discovery` (which re-exports `browse_rung`), and `cerulion_netd::discovery_fold` gains `fold_discovered_peers` and `fold_discovered_peers_at`, replacing `fold_cached_peers`; `PeerFold`'s `folded_cached` and `dropped_cached` are renamed `folded_discovered` and `dropped_discovered`.
- The wire header grows from 32 to 40 bytes (wire header version 2): `WireHeader` gains `step_tag` at byte 32, a `u64` holding the producer rank in bits 48 to 63 and the step plus one in bits 0 to 47, so `0` means untagged (`cerulion_core::wire::StepTag`). Every frame this release publishes is untagged. `WireHeader::SIZE` is 40, so the smallest `max_slice_len` is 40 (it was 32): a graph, a `CERULION_RMW_SLICE_CEILING` entry or a bridge mapping below 40 is refused as before. Releases with the 32-byte header cannot exchange frames with this one. Where this release can see the other side's version it refuses loudly: the node cdylib ABI moves to 28, so every prebuilt node cdylib must be rebuilt (`cerulion node build <type>`); every iceoryx2 data service this release creates carries a `cerulion.wire_header_version` attribute, and an opener refuses a service stating another version (one stating none, made by a raw iceoryx2 program or an older release, is accepted with a warning that its frames are assumed to be this layout); zenoh frames move to the `cerulion_w2` key namespace and a demand GET states its version (a producer at another version answers `refused:wire-header` and enables nothing); the iroh plane's ALPN is `cerulion/wire/2`; the `cerulion-netd` banner states `wire_header` and its protocol version is 8, and a client refuses a daemon at another wire header version; a robot's catalog states `wire_header_version`. These checks run in the newer process only: an older process opening something this release created reads no version and is not refused, so run one Cerulion release per machine and the same release on machines that talk to each other. Bags record a version 2 schema descriptor (20 bytes, with the wire header version); a bag recorded with the 32-byte header still reads, and its frames are upgraded to the 40-byte layout as they are read: a message stream upgrades one message at a time, and a frame walk (`bag play`, `--resim`, the Python frame iterator) builds one upgraded copy of the bag's frames per open bag, reserved at its exact size and held until the bag is closed, and refuses a bag whose copy would pass 2 GiB, naming `cerulion bag migrate`. A frame with bytes after its declared size is upgraded with them kept after it; one shorter than the header or declaring a size past its end is served unchanged and counted. `bag info` reads the recorded bytes, names the upgraded topics and the memory a walk would hold, and reports a bag of any size. `cerulion bag migrate` writes a current copy of such a bag, a graph-less `bag record` bag included, records the upgraded topics in the migration record (whose two graph digests are now absent for a bag with no graph), and refuses a bag holding a frame it cannot upgrade. `cerulion_bag` API: `SchemaDescriptor` gains `wire_header_version`, and its `descriptor_version` field is now private, read with `SchemaDescriptor::descriptor_version()`; `BagError` gains `UnsupportedWireHeader` and `LegacyUpgrade`; `BagReader` gains `legacy_wire_header_topics`, `legacy_passthrough_count`, `has_readable_footer` and `user_frames_as_recorded`, and the crate exports `LEGACY_UPGRADE_CAP_BYTES`. `cerulion_core::wire` exports `WIRE_HEADER_VERSION`, `V1_HEADER_SIZE`, `upgrade_v1_frame_into`, `upgrade_v1_frame` and `FrameUpgradeError`. The permissive `cerulion-wire` crate mirrors the change: `WireHeader::SIZE` is 40, the struct gains a public `step_tag: u64` field (code that builds a `WireHeader` with a struct literal must add it) and the crate exports `WIRE_HEADER_VERSION`. The Python client exposes `Frame.step_tag`, `Record.step_tag` and `cerulion.WIRE_HEADER_VERSION`.
- zenoh moves from 1.8.0 to 1.10.1, the first release with mixed-reliability QUIC, and `cerulion_core` compiles zenoh's `transport_quic`, `transport_quic_datagram`, `transport_udp` and `unstable` features beside `transport_tcp`. zenoh-transport 1.10.1 depends on lz4_flex 0.10.0, which RUSTSEC-2026-0041 covers and which has no patched 0.10 release; the affected functions compile only under zenoh's `transport_compression` feature, which nothing enables, and `tools/release/deny.toml` carries an exception for that one advisory until zenoh moves to a patched lz4_flex. The same file accepts RUSTSEC-2025-0134 (rustls-pemfile, unmaintained, no vulnerability), which zenoh-link-commons 1.10.1 uses to read certificate files. quinn-proto moves from 0.11.17 to 0.11.19, the release that fixes RUSTSEC-2026-0340 and RUSTSEC-2026-0343, now that QUIC carries graph traffic.
- A Rust port of a package-less workspace YAML schema is scaffolded as `use native_ros2_messages::<Name>;` (the type generated at the message crate's root) instead of `use <Name>;`.
- A publish rings its topic's shared memory doorbell for every topic a graph produces while the doorbell is on, where it used to ring only for a topic a sibling process in the same deployment was planned to read. A consumer in a graph nobody planned alongside the publisher, an `rmw_cerulion` wait set and any other blocked reader are woken by the publish rather than at the end of their own recheck period. The page a consumer opens is unchanged: a declared trigger or sync input topic that admits a writer outside its process. A topic that admits outside publishers is armed with shared ownership, so a graph's exit leaves the page for the other publisher. A publish on a topic nobody is blocked on costs one atomic and one cached backend read, with the kernel wake held behind the page's parked claim, and the live loop's wait policy line reports both the number of topics armed and the number the plan named as read by a sibling group.
- An input that declares no trigger no longer creates an event listener. Such an input is read on its own node's fire by the step's snapshot and is woken by nothing, so the port that would sit in every publisher's notify path for it is not created at all; a topic's live listener count and its expected in-process total both drop by one per such input. `CerulionSubscriber::wait_for_message`, and `AnySubscriber::wait_for_message` which forwards to it and is the method a node body can reach through the prelude, now return an error naming the topic ("this subscriber was built with no event listener, so there is nothing here to wait on") instead of waiting out its timeout and returning `Ok(0)`. That entry serves subscribers a tool builds for itself, the `cerulion topic` observer among them; a node reads a declared input through its own tick or has the step drain it.
- A recording writes a read-log record at every gated consult a replay of it also makes, the ones that found the queue empty included, so a replay can tell a read the candidate never made from one the recording never held. The one empty consult left unrecorded is a burst's between-fires refill: a live burst discovers its own length by asking until the answer is empty, while a replay fires the recorded count and never asks, so recording it would leave a position no replay could fill, and a per-set Sync node has no refill hook at all, so a replay of its planned fires runs no align pass behind them. Bags recorded by this build stamp `trace_format` 7; a Cerulion that reads up to 6 refuses such a bag up front with "recorded by a NEWER Cerulion; upgrade to replay it" (exit 2) instead of replaying it under the wrong contract. This build replays every earlier format exactly as before, and on a format 7 bag a consult the recording holds no read for is a schedule divergence (exit 6) rather than the counter it used to be.
- The node cdylib ABI is 28; Cerulion 1.0.0 loads ABI 22. Several changes in this release, the read log and the wire header above among them, alter what crosses between the host and a node, so every prebuilt node cdylib must be rebuilt (`cerulion node build <type>`) before it will load.
- The processes of a multi-process run start their first step at one shared instant. The supervisor's start signal to its workers changes from a plain `go` file to `cerulion-go-v1 epoch_ns=<instant>`, an instant 20 ms after the supervisor writes it, and every worker waits for that instant before its first step, so the processes that are ready by then start together. A free-run `--record` process that arrives later than the graph's tightest declared timing (at least 1 ms) logs how late it was and starts its own timeline, with no burst of catch-up steps. The supervisor and its workers must come from the same release: a worker from this release refuses the plain `go` file an older supervisor writes and does not start, and a worker from an older release does not wait for the shared instant.
- The minimum supported Rust version is 1.95 (it was 1.93), and the release workflow builds with Rust 1.95.0. `cerulion_core` calls `try_update` on its atomics, the name Rust 1.95 stabilised and Rust 1.99 uses in place of the deprecated `fetch_update`; a workspace that denies warnings builds again under the current stable.
- The shared memory transport moves to iceoryx2 0.10.0. Every event service is sized to the event
  ids the transport actually mints rather than the library default, so a listener no longer walks
  256 shared memory counters on every wait.
- The install script links `cerulion`, `cerulion-netd`, `cerulion-connectd` and `cerulion-remoted` into `~/.local/bin` (and into `/usr/local/bin` when that directory is on the PATH, writable without `sudo`, every account can reach the install directory, neither `~/.local/bin` nor another `cerulion` is on the PATH, and no other account can change `/usr/local/bin`, the install directory or a linked program; otherwise it makes only the `~/.local/bin` links, with a warning when another account could change one of those paths), so a shell that already searches either directory runs `cerulion` as soon as the install finishes. Its last line now says whether `cerulion` is ready in the terminal that ran it, and names the one command that fixes it, `. ~/.cerulion/env` (`source ~/.cerulion/env.fish` in fish), only when it is not. The README one-liner ends with that command, so it leaves `cerulion` on the PATH of the terminal it was pasted in. A name in either directory that is not already the installer's own link is left alone, and `--no-modify-path` skips the links as well as the startup files.
- `cerulion topic echo` prints each frame as one YAML document: a `# seq=.. ts=..ns schema=0x.. size=..` comment, a `# <type>` comment, the fields with no indent, then `---`. Gap notices and the hex of an undecodable frame are `#` comments. An array longer than `--truncate-length` (default 128) ends in `!truncated <n>`. `std_msgs/String` and `sensor_msgs/Image` print in full like every other type, not as one-line summaries. This changes the command's output, which SemVer covers: a script that parsed the old lines should read the output as a stream of YAML documents and skip `#` lines.
- A multi-process `graph run` free-runs by default. This covers a graph with `process_groups:` and an unpartitioned graph that `graph run` partitions on Unix. Each worker process steps on its own wall-following clock, with no shared per-step barrier. Set `CERULION_EXECUTION_MODE=lockstep` to get the 1.0 barrier behaviour back. `run.json`'s `gating` reads `recorded_wall` (or `wall` under `--no-rings`) instead of `quantum`. `--record` bags stamp `coordination: free_run`, which `bag play --resim` follows. `--single-process` runs are unchanged. This changes the default behaviour of `graph run`, which SemVer covers.
- A node that returns `NodeError::Fatal` is stopped. The scheduler logs one error line naming the node and never fires it again, and the rest of the graph keeps running. When the run ends, `graph run` prints `Error: node '<id>' stopped on a fatal error: <message>` for each stopped node and exits 3, where it used to exit 0. A failure that fails the run still exits 1. This changes how a node's error is handled and the command's exit status, which SemVer covers.
- `cerulion graph run` on a graph without `process_groups:`, and `graph run --auto-partition`, run the derived multi-process layout in memory without asking, in a terminal or a script, and leave the graph file unchanged. Before, a terminal run showed the partition diff and asked whether to write it. Add `--yes` to save the layout into the graph YAML (with a `.bak` backup); `cerulion graph partition` still offers the interactive save. This changes the command's behaviour, which SemVer covers.
- The machine key moves from `~/.cerulion/desk.key` to `~/.cerulion/identity/device.key` (0600, in a 0700 directory). On first use an existing `desk.key` is adopted byte for byte, so paired robots keep trusting it, and `desk.key` stays, as a hard link to the same key or an identical copy; two different keys under the two names are refused, naming both files. The config directory itself does not move, but `cerulion pair` and `cerulion connect` now honour `CERULION_HOME` for the key, `robots.toml`, `config.toml`, `epochs/` and `ros2/` (they used to read `~/.cerulion` regardless), so move those files if you set `CERULION_HOME`. To start a new key, remove both key files.
- State records, the restore points a mid-run resume reads, carry the writing worker's rank and a format version, and their header grows from 32 to 40 bytes. A mid-run bag recorded by Cerulion 1.0 can no longer resume from its state records: `cerulion bag play --resim` refuses it, naming both format versions, and the fix is to record it again. Replaying such a bag from its start is unchanged.
- Re-executing a free-run recording with `cerulion bag play --resim` delivers each frame one node sends to another in the same worker process at the step the recording read it, and holds back a frame that arrives early. A recorded read the re-execution does not reproduce exits 6 and names the edge, the step and both sequences. A read log that cannot be enforced on such an edge is refused with exit 2. The `--report` JSON gains `read_log_enforcement`, always present, and `read_log_verdict`, present only when the read log finds a schedule divergence (exit 6). Lockstep recordings are unchanged.
- On macOS 14.4 and later, a worker process of a multi-process run that is waiting for data wakes on the publish instead of on its recheck timer: the publisher bumps a wake word in the topic's shared memory doorbell page, and the kernel wakes the blocked consumer. `CERULION_DOORBELL_OS_SYNC=0` turns this off on macOS only; `CERULION_DOORBELL=0` turns the doorbell off on every platform.
- One parser reads schema YAML everywhere, and it refuses three shapes that used to load silently, naming the schema: an entry that is not a mapping, a `fields:` written as a list (`fields: []`), and two fields with the same name. `schema info` on such a file exits with the error; `graph run`, `schema list`, `topic` and `node create` warn, skip that file and load the rest. An empty `fields:` is still valid.
- `cerulion ros2 attach --dry-run` runs from any directory, so listing a robot's DDS topics no longer needs a workspace. Outside a workspace it uses one empty temporary directory under `TMPDIR` and removes it on exit; if that directory cannot be created it refuses and says to point `TMPDIR` at a writable location or run from inside a workspace. Writing or running the bridge graph still requires a workspace.
- In `cerulion_core`, `DoorbellRegistry` loses `primary_addr` and `primary_topic`: look a topic up by name with `addr(topic)` or the new `bell(topic)` and `slot_of(topic)`. `CrossProcessWiring::with_sibling_topics` and `ValidationOptions::sibling_topics` take the new `SiblingProducedTopics` instead of a `BTreeSet<String>`, and a new `SiblingConsumedTopics` sits beside it. Both are built with `.collect()` from `String`s and serialize as the bare set.
- The viewer's 2D and 3D views always use the stage colour `#0b0d11` (it was `#10161f`), including views in a layout set with `set_blueprint`, which used to get the viewer's dark gradient. Point clouds coloured by intensity start at cerulean `#00c0ff` instead of pure blue; the green and red stops are unchanged.
- The README's Debian and Ubuntu recipe uses the archive at `https://apt.cerulion.com`. It installs the archive key only after checking its fingerprint (`953C69FD279D9256FA4B71C5DA5FDE5D0DC6D91B`), so a failed download no longer leaves an empty keyring that breaks `apt-get update`. A machine set up with the 1.0 recipe, whose `/etc/apt/sources.list.d/cerulion.list` names the older address, can switch by running the new recipe.

### Known issues
- On macOS, a node cdylib built against the released iceoryx2 0.10.0 can fail to create a port
  after the host closes a descriptor that node opened. iceoryx2 0.10.0 keeps a macOS-only table of
  shared memory descriptors in every copy of the library, the host and each node cdylib link their
  own copy, and a descriptor closed through a node's copy left a stale entry in the host's table,
  after which the host failed to create topics. The release binaries are built against a fork of
  iceoryx2 that repairs a stale entry in its own table, and workspaces made by
  `cerulion workspace create` or `cerulion workspace init` build their nodes against the same fork,
  so `cerulion graph run` with plugin nodes runs. A node cdylib built against the released iceoryx2
  0.10.0 keeps the unfixed table in its own copy. That includes every workspace made by Cerulion
  1.0, whose root `Cargo.toml` has none of the iceoryx2 `[patch.crates-io]` entries these commands
  now write: copy that block from a workspace made by `cerulion workspace create` and rebuild its
  nodes. Linux is not affected. The cause is eclipse-iceoryx/iceoryx2 issue 2034, and this note
  goes away when an iceoryx2 release carries the fix.
- Publishing a message allocates once, on every platform. The allocation is inside iceoryx2
  0.10.0, which builds a small shared cell per loan; 0.9.1 did not, and there is no way to avoid
  it through the library's API. It costs 14 to 19 nanoseconds and it is on the publish path, so a
  program with a hard real time budget should know it is there. The cause is
  eclipse-iceoryx/iceoryx2 issue 2035 and this note goes away when it is fixed.

## [1.0.0] - 2026-09-21

The first release of Cerulion. Its crates, binaries and Debian packages come from this tree.

### Changed
- The crates live under `crates/`, the tooling under `tools/`, and the user API reference under `docs/user-api.md`.
- The always-on window recorder is pinned and niced, and the dead-node walk left the live loop, so the multi-process round trip stays flat with the recorder on.
- A credit-blocked producer parks on the credit word instead of polling.
- A Flashback capture reads its frames after it snapshots its trace, and its coverage manifest marks every exit that left the close's final drain incomplete.
- The network posture pair and the service drain-all take halves were removed (ABI 21); services take one message at a time by design.
- Comments and documentation no longer carry internal tracker identifiers; the repository root holds the license, the readme, the changelog and the build manifests, with community files under `.github/` and legal files under `docs/legal/`.
- The default log filter is quieter: the per-topic producer reconciliation is one compact line of counters, the recorder's clean finalize keeps its one completion line, and startup, worker drain, exit hygiene and clean-finalize bookkeeping moved to `debug`, so `recording written to <path>` is the last line of a recorded run and a verification's `replay PASS` is no longer preceded by paragraphs of accounting. The long-running verbs still print their `info` lifecycle lines (worker spawn, trace ring and ready-file names, topic provisioning, daemon boot). The daemon's first-use spawn is reported at `info` (a boot still waiting after two seconds is reported at `warn`, so the quiet verbs are never silent for the whole readiness wait), the zenoh no-listener line is filtered by default, and a node cdylib announces its log filter only when `RUST_LOG` is set. The multi-process supervisor's planning build no longer prints a reconciliation line for a graph that never ran. Release builds compile `debug` out (`tracing`'s `release_max_level_info`), so the demoted lines are absent from a release build of `cerulion` (which hosts the recorder, `cerulion bagd`) and of `cerulion-netd` at any `RUST_LOG`; binaries built without cargo's `--release` keep them. The `debug-logging` cargo feature cannot lift that ceiling, and the documentation no longer says it can.

### Added
- Every `cerulion` command runs under an account. `cerulion login` signs a machine in once, with a short code to approve from a browser on any machine; later commands read the result locally and keep working offline. `login`, `completions`, `--help` and `--version` need no account.
- The release installer provisions the compiler that built the release. Every platform archive now carries the compiler metadata of its own build beside the binaries, and `install.sh` installs that exact rustc and its Cargo through rustup, verifies the full commit hash, and only then activates the binaries, so the compiler that builds your nodes is the one that built the CLI loading them. A failed setup leaves the previously installed binaries in place, though a partly installed Rust toolchain can remain under rustup's own management. Existing rustup defaults, profiles and shell startup files are left alone, `CARGO_HOME` and `RUSTUP_HOME` are honored, and an installation that carries Rust without rustup is refused rather than replaced. Archives from before the metadata still install their binaries, with a warning that they cannot set Rust up.
- The launch readme with the benchmark evidence packages, the benchmark charts on three platforms, the ROS 2 compatibility page and the second architecture panel.
- New workspaces select the compiler that built the CLI. `cerulion workspace create` and `cerulion workspace init` write a `rust-toolchain.toml` naming that release with the minimal profile, so `cerulion node build` inside the workspace uses it without an environment variable. The file is written only when a rustup toolchain whose release and full commit hash match the CLI is already installed; the check is offline, installs nothing, and leaves rustup's default alone. A missing, custom, nightly or beta compiler produces a warning instead, and an existing `rust-toolchain` or `rust-toolchain.toml`, symlinks included, is preserved. Workspaces created before this keep using an explicit `RUSTUP_TOOLCHAIN=`.

### Fixed
- A graph could abort with no panic text and no backtrace when the `cerulion` host and a node cdylib had been compiled by different rustc releases. A node crosses that boundary carrying Rust types whose layout the compiler chooses, and two releases can agree on every struct size and offset and still encode one of those types differently at run time, so the existing ABI-version check passed and the host then read a value the node never wrote and freed memory that was never initialized. A node cdylib now reports the compiler that built it, and the loader refuses a node whose compiler differs from the host's, naming both compilers and the two ways out: rebuild the node with the host's compiler, or reinstall the CLI with yours. `cerulion node build` also warns when the `rustc` on `PATH` reports a different release, while leaving Cargo's own compiler selection alone. This takes the node cdylib ABI from 21 to 22, so every prebuilt node cdylib must be rebuilt (`cerulion node build <type>`) before it will load.
- The examples cargo-check job skips the Go2 workspace and manifest-less directories; the fuzz job enters the crate at its new path.
