# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Changed
- Declared graph ingress precreates canonical single-writer services at the complete consumer capacity. Authenticated wire forwarding honors a declared reliable queue policy and reports refused frames. Embedded Android starts refuse ingress without a supported path.
- Declared authenticated imports require native single-writer provisioning; a multi-publisher service with one live writer remains readable by observers.
- Shared outbound readers survive refused operations and metadata discovery failures, retain the server against idle shutdown, and keep imported topics bound to their source robot's access policy.

- LAN topic access defaults to paired on every platform. Unpaired LAN peers
  cannot demand topics or publish into graph ingress through the zenoh plane.
  Paired desks use the authenticated remote plane. Explicit
  `CERULION_LAN_ACCESS=open` remains available for development and warns at startup.
- Networking guides and the Go2 graph pair describe automatic account and saved
  pairing discovery, authenticated declared imports, shared serving and consuming,
  and explicit open-LAN compatibility without requiring addresses for paired access.

### Fixed
- Local-only graph and node runs exclude their topics, schemas and run metadata from every remote serving plane, including an already running open gateway. An enabled `network:` block's egress list is enforced for that producing run by other daemons too.
- Network-enabled runs start the authenticated remote server on their first egress registration without requiring `CERULION_NETD_LISTEN`. Query-only desks and local-only runs start no server; the last serving registration's release or disconnect reaps it after active work, owed e-stop delivery and its latch clear. Saved robot pairings and expired saved logins preserve offline serving. Owned remote servers receive SIGTERM and a bounded graceful cleanup window before forced reap.
- Topic discovery lists account-owned and explicitly paired robots anywhere, with direct or relayed reachability and visible offline status. Topic reads and remote visualization demand authenticated wire/2 streams automatically, keep identical local and remote names separate, and release streams when their observers exit. `topic echo`, `hz`, and `info` accept `--robot NAME` and refuse ambiguous names with exit 2.
- A machine serving authenticated remote topics can also consume topics through
  the same device endpoint. Outbound mirror release preserves incoming serving.

## [2.0.0] - 2026-11-11

Semantic Versioning covers the graph YAML format, the `cerulion` command line and the node macros of `cerulion_macros`. This release changes the command line in ways a script written for 1.x notices, among them the output of `cerulion topic echo` and how `cerulion graph run` runs a graph by default (see Changed), so it is a major version. The lower-level Rust API of `cerulion_core` is not covered by SemVer yet, and neither are the library crates behind the command line and the daemons (`cerulion_cli_engine`, `cerulion_wsd`, `cerulion_netd` and `cerulion_bagd`) or the bag library `cerulion_bag`. This release changes public items in each of them, so Rust code that calls them directly may need edits. Prebuilt node cdylibs are a separate matter: every one must be rebuilt for node ABI 31 (see Changed).

### Added
- `cerulion bag play --resim all --verify --feed-index-budget <BYTES>` bounds the memory a fed replay's index of the bag's frames takes; the default is 1 GiB (1073741824 bytes). The index holds only the frames the replayed reads consume, up to `--duration` when it is given, one sorted key and one slot per frame, 40 bytes on a 64-bit build, and the budget charges those bytes and 40 bytes for each producer label of the topics the reads consume, which the index build reads to tell a topic's writers apart. A replay whose reads need more is refused with exit 2 after the labels are read and before the bag's frames are walked (`read_identity_feed_index_budget`), and the refusal names the bytes the reads need, the frame identities and labels they are charged for, the budget and `--feed-index-budget`. The flag needs `--resim` and `--verify`: plain playback and a resim without `--verify` feed no reads.
- `cerulion_pairing` keeps team credentials in the machine identity directory: `identity/active_team` names the team, and `identity/<team>/leaf.der` and `identity/<team>/bundle` hold the leaf certificate and the trust bundle (mode 0600). `IdentityLayout::load_team_credentials` accepts them only when the bundle verifies against a trusted root set, the leaf belongs to the bundle's current generation and certifies this machine's key, and a leaf other than a robot's has not expired; each refusal names the file. `TeamTrustBundle` carries `next_ca_der`, the next generation's issuing CA. A release build trusts no root set yet. The `dev-issuer` feature adds a local development issuer and the `cerulion-dev-issuer` program (`init`, `init --import`, `status`) that enrolls machines into one development team; no release binary is built with it, and the release workflow checks that.
- `tls/<host>:<port>` is a carrier: TLS 1.3 over TCP, for a path where UDP does not get through. It reads the same `tls:` files as `quic/` (`certificate` and `private_key` for a listener, `root_ca` for a connect) and graph-load validation applies the same file rules to it.
- `cerulion_core::NetworkConfig` gains `auth: Option<NetworkAuth>`. `TeamAuth::new` checks a machine key, its team leaf certificate and the team's anchors (`TeamAnchors`: the current issuing CA, retired CAs and, during a rotation, the next or the previous generation's CA) with the `cerulion_pairing::team` profile. A machine opens up to three team sessions on separate listeners, each on `quic/` and `tls/` only, with both ends presenting and verifying a certificate, the keys passed to zenoh in memory and never as files, scouted and gossip-learned peers never dialed in any mode, and a generated zenoh access policy that denies by default and is keyed on the peer certificate's common name. `NetworkAuth::Team` is the data session: a listener accepts only leaves the current issuing CA signed, and the policy admits only current-generation names. A viewer or ci leaf receives data and may query; an operator leaf may also put and answer queries; an owner or robot leaf may send every message. `NetworkAuth::TeamCrossGeneration` carries data with the other live generation during a rotation: it trusts only that generation's CA and admits only that generation's names, so a leaf the next generation's CA signs with a current-generation name fails the data session and is denied every message on the cross session. `NetworkAuth::TeamBundleLane` trusts the retired CAs and the other live generation's CA and admits only the bundle exchange on `cerulion_auth/bundle`, so a leaf a retired CA signs never reaches a data, demand, announce or query key, whatever name it carries; it can still answer a bundle query, whose reply a consumer must check with `cerulion_pairing::team::verify_team_trust_bundle`; nothing in the command line or the daemons consumes a bundle reply yet. zenoh matches the common name, not its issuer, so a live CA's key can issue any name of its own generation. A dialer also trusts the public Web PKI roots, which zenoh's TLS and QUIC clients always load: a listener whose certificate chains there links, matches no team name and is denied every message, so such a dial stays up and carries nothing. A `tcp/` or `udp/` locator, a datagram-only `quic/...?rel=0` locator, a locator with a `#` endpoint config, or certificate files set beside team credentials fails the session open naming it. Nothing in the command line or the daemons sets `auth` yet, and `graph run` refuses to hand it to a gateway child. `cerulion_core::transport::test_ca` (feature `test-helpers`) issues test team credentials in memory.
- Exact replay of one ROS 2 process over `rmw_cerulion`. `cerulion ros2 run --record-deliveries <DIR> <pkg> <exe> ...` (also on `ros2 launch`, or `CERULION_RMW_DELIVERY_LOG=<DIR>` on any launch path) records what each process consumed, in the order it consumed it, into `<DIR>/<exe>-<pid>.rdl.mcap`: every take with its payload, every `rmw_wait` return, the answers to five graph queries (`count_publishers`, `count_subscribers`, `service_server_is_available` and the two matched-endpoint counts; every other graph query is answered live during a replay), and a hash of every output. `cerulion ros2 run --replay-deliveries <LOG> <pkg> <exe> ...` (or `CERULION_RMW_REPLAY=<LOG>`) runs that process alone against its log: each wait reports the recorded readiness at once, each take is served from the log, and each callback's outputs are compared with the recording; the verdict, `identical` or the first node, topic and window whose outputs diverged although its inputs matched, is written to `<LOG>.verdict.json`. Several single-threaded executors on several threads replay in the recorded order, and a callback that blocks on another thread is named after 5 s. A log of another process (command line, `ROS_DISTRO` or library build) and both variables set are refused by name at `rmw_init`. A multi-threaded executor or a serialized take seen while recording marks the log not replayable, so its replay is refused at `rmw_init` under that cause; a multi-threaded executor first seen during a replay fails `rmw_wait` there. An rclcpp `MultiThreadedExecutor` whose callbacks finish in microseconds runs as one thread and is not detected. A replay in which a thread outside every executor publishes ends `refused`, naming the thread's first topic, and the replay of a log torn by a killed recording compares each thread's last surviving segment only as far as the log goes, ending `log_exhausted_early` if everything before the cut matched. A replay writes a `running` verdict when it starts, so a replay that crashes never leaves an earlier verdict (one that cannot write it is refused at `rmw_init`), and it publishes its outputs live, so keep it away from a live robot. With neither variable set, the cost is one check per rmw call; while recording, each take copies its payload into the log and each output is hashed on the calling thread, which lifts a 1 MiB round trip from about 165 µs to 3.0 ms on the test host (`docs/ros2_replay.md`, "What recording costs"). Runtime-tested on Humble with rclpy and rclcpp nodes, rclcpp's `/clock` thread under `use_sim_time` included, and with rclpy and rclcpp service clients and servers; see `docs/ros2_replay.md`.
- `rmw_cerulion` gains an opt-in `period-park` Cargo feature that wakes a subscriber sooner on a topic published at a steady rate. It is off by default and the release packages do not enable it; build the library with `cargo build --release --locked -p rmw_cerulion --features period-park`. On Linux, `rmw_wait` learns each subscribed topic's arrival period. Once a topic is regular (eight gaps in a row between 200 µs and 100 ms, with a smoothed deviation of at most an eighth of the smoothed period and at most 25 µs), each wait sleeps in the kernel `ppoll` block until shortly before the next expected message, then parks on that topic's doorbell for at most 200 µs, so the publish wakes it from the park rather than from the kernel block. A topic that is not regular, `CERULION_MONITOR_WAIT=0`, an x86 CPU without `UMWAIT` and a wait set of more than 16 subscription topics keep the stock wait.
- Generated messages with only fixed fields gain `<Name>Shm::read_unaligned(&[u8]) -> Option<Self>`, which copies one value out of bytes at any address, such as one element of `PoseArray.poses_bytes()`, and returns `None` for a source shorter than the message.
- Nodes that share a process can run in executor units, which are opt in: without a profile the nodes of a process run as one unit, one level loop, as before, and units form only from the graph's profile (`graphs/<name>.costs.yaml`) or a node's `isolate: true`. A graph that already has `graphs/<name>.costs.yaml` (the profile the cost-fused partitioner reads) therefore now runs its processes in the executor units that profile forms in a free run on the real clock, and such a run, when it derives its process groups from the profile (a graph without `process_groups:`, or `--auto-partition`), can derive other groups than before, since the partitioner keeps each linear chain within the per-group budget in one group (see the entry on linear chains below). Without that file each process runs as one unit again unless a node of it declares `isolate: true` (`graph partition --costs <path>` reads a profile moved elsewhere), but the default run of a graph without `process_groups:` then derives one process per node, so a graph that keeps cost-fused groups declares them (`cerulion graph partition <name> --yes` writes the groups the cost rules derive). With the file kept, `isolate: false` changes no process group; declared on every node that another node of its process triggers, it keeps that process in one unit when no node of it declares `isolate: true` and its trigger and `block` edges connect all of its nodes, and it never joins nodes that no such edge connects. A node that declares `isolate: true` runs in a unit of its own, so its ticks no longer hold the other nodes of its process. Each unit runs on its own thread with its own step counter, clock and trace ring, and units are joined by the same bounded drop-oldest queues that join processes, so a recording of such a process is a bag with one rank per unit and replays like a process-per-node bag. A unit waits for a frame from another unit as a process waits for one from another process: its park takes the wake on its first declared trigger or sync input that another unit or process writes and sees a frame on any other input when its current wait ends (within 20 µs on an x86 host with a monitor-wait instruction, within one event-stream period, about 130 µs, on an Arm host whose WFE park has no timeout, and one 100 µs recheck plus the kernel timer's overshoot elsewhere), so a join with two or more such inputs can wait that long when its set completes on one of them but the first (https://github.com/cerulion-inc/cerulion/issues/755); inside one process a join has two or more when, for example, its unit holds none of its producers: it declares `isolate: true`; with a profile, no `isolate: false` or `block` edge keeps it with its producers; without one, it runs past an isolated node's level in a later unit that holds none of them, or its producers all declare `isolate: true`. With a profile, `isolate: false` on the join keeps it in the unit of the nodes of its process that trigger it, where the joined unit keeps its band of levels (below); without one a join runs in its process's unit unless it declares `isolate: true` or runs past an isolated node's level in a later unit, and `isolate: false` changes nothing. On an oversubscribed host each hop between units can also wait one scheduler quantum for the reading unit's thread to run, which a process that runs as one unit does not pay; that wait is the p99 of a run in units on a loaded host. With a profile every node starts a unit, and a linear chain (one producer handing each frame to one consumer that fires on it; the fused-chain census and the partitioner start from the same link rules) merges into one unit, where a hop runs on the level loop with no wake, only when the profile shows the unit's summed tick stays under a quarter of the shortest period the merged unit is fed at (each member's own period, the profiled rate of each trigger edge into a member, and the profiled fire rate of a member no graph node triggers or that fires on a topic no graph node publishes) and of the tightest `tick_within_ms` of its members, and only where the merged unit keeps a contiguous band of the graph's levels in which, on levels derived from the trigger edges, each node above the band's first level is fed from inside the unit at the level below (a link that would break it stays split, an `isolate: false` join is held to the same band, and `graph plan` says why); a process whose split the partition validator still refuses, as when a `block` edge keeps nodes on both sides of a level in one unit, runs as one unit, which `graph plan` prints and a run logs at warn, naming the process and each node of it that declares `isolate: true`. A `block` edge's producer and consumers stay in one unit, `isolate: true` included, and a merge into that unit counts the ticks of all of them. Units are fixed when the graph loads. Units form, from a profile or `isolate: true`, in a `process_groups:` group with more than one node, a cost-fused group, and under `--single-process` on the real clock; process-per-node graphs, the lockstep execution mode and the virtual and external time sources run as before. Under `--single-process` a graph whose nodes split into several units runs them all in one worker process beside `graph run`, its recording embeds one process group holding every node and records one rank per unit as a multi-process run does (so the single-process refusal of a graph that reads a topic no node in it publishes does not apply to it), and the run still says that the auto-partition default is skipped (or that the declared `process_groups:` are not executed); a graph that is one unit runs in the `graph run` process as before. Flashback checkpoints are not taken in a run where a process hosts more than one unit. A process that hosts several units sizes its file descriptor table before its unit threads start (to the soft `RLIMIT_NOFILE`, at most 65536 slots), so no unit's first publish waits for the kernel to grow a table its threads share; `cerulion_core::fd_limit` gains `presize_descriptor_table`, `presize_target`, `PresizeOutcome` and `DESCRIPTOR_TABLE_PRESIZE_CAP`. When a node stops on a fatal error, the run's verdict names the process group of the process that hosted it, once; a `--single-process` run prints only the node's own line, as before, and exits 3 (`CliError::WorkerNodeFatalAnnounced`).
- A node's `isolate:` key in the graph YAML: `isolate: true` gives the node an executor unit of its own, with or without a profile (a unit runs a contiguous band of the graph's levels, each node above the band's first level fed from inside the unit at the level below, so without a profile a node past the isolated node's level runs in a later unit when no node of the process's unit feeds it at the level below and that unit starts at a lower level, and `graph plan` says so); with a profile, `isolate: false` keeps it in the unit of the nodes that trigger it, whatever the profile's split says, where the joined unit keeps its band of levels: a node joins only the producers whose units keep it, and one that joins none of them runs in a unit of its own, which `graph plan` says. Without a profile `isolate: false` changes nothing.
- `cerulion graph plan <name>` prints the processes a free run of the graph starts, the executor units inside each, where they come from (one unit per process without a profile, apart from each `isolate: true` node, or the graph's profile), and why each unit starts.
- When `graph run` derives process groups from a graph's profile for a run whose processes execute in executor units (the free run on the real clock), the cost-aware partitioner keeps every linear chain whose summed cost is within the per-group compute budget in one process group, unless the merged group could not run as one worker (a chain over the budget is cut where the cost model cuts it, and a chain is cut at a node the profile isolated, which keeps a process group of its own unless a `block` edge puts it in one group with that edge's producers and consumers; a chain is then cut at every node of that group, and only the cost rules can add another node to it); the executor units then split the chain inside the process where the profile says a merge is unsafe. `graph partition`, the lockstep execution mode and the virtual and external time sources partition as before. `cerulion_core::graph` gains `auto_partition_with_options` and `AutoPartitionOptions`, and `cerulion_cli_engine::partition_emit` gains `derive_emit_groups_with` and `run_auto_partition_preflight_with`.
- `cerulion doctor` checks this host for problems that slow or stop Cerulion and prints the fix for each: the open-file limit against every workspace graph, `/dev/shm` size, dead iceoryx2 nodes, a `config/iceoryx2.toml` in the current directory that moves the shared-memory root, the filesystem recordings land on, the local sign-in state, and the CPU frequency governor (reported, never judged). Each check reports `pass`, `info`, `warn`, `fail` or `skip` with why it matters; `--json` prints a versioned report, `--check ID` runs one check, `--local` skips the checks that use the network and `--timeout-ms` bounds the run. It exits 1 when any check fails, needs no root, writes no file, changes no sysctl or network setting and runs on a machine that has never signed in.
- `cerulion doctor` also checks the kernel clock (synchronised or not, read with `ntp_adjtime`, which changes nothing), whether each IP interface's MTU can carry a QUIC datagram (1228 bytes), the NVIDIA driver, devices and CUDA toolkit and whether the loader cache names `libcuda.so.1` on a host with a GPU it can use (from files, with no CUDA library loaded), the sourced ROS 2 distribution, and whether `librmw_cerulion.so` is where `cerulion ros2 run` looks.
- `cerulion doctor` also reads the device certificate (expired, not yet valid, or issued for another device key), asks a running `cerulion-netd` for its status without starting one, and reports whether `cerulion-remoted` is installed and, on Linux, running. `NetdClient::status` returns the daemon's whole `status` answer.
- `cerulion doctor` has two network checks, which `--local` and `CERULION_NETWORK=off` skip: `net.mdns` browses `_cerulion._tcp` for one second and warns when the browse cannot start or its responder stops mid-window, and `net.udp` sends one QUIC version-negotiation datagram to each `quic/` or `udp/...?rel=1` connect locator of the workspace's graphs and each `--udp-target HOST:PORT`, and warns for an endpoint that does not answer. The probe needs no handshake or certificate; `cerulion_cli_engine::doctor::udp_probe` exposes it. Both checks print robot names, endpoints and resolver errors with each control character replaced by U+FFFD, so a LAN peer or a graph file cannot put terminal escapes in the report.
- `cerulion doctor` checks `net.ipv4.tcp_slow_start_after_idle` on Linux and warns when it is nonzero, with the fix the `graph run` warning for `tcp/` egress prints.
- `#[input(trigger, consume = latest)]` fires a data-triggered node at most once per scheduler step and serves the newest queued frame; the older frames that read drained are not served. `consume = fifo`, one fire per queued frame in arrival order, stays the default. A frame no fire has read yet, because `throttle_ms` or a `block` gate deferred the fire, is kept until a newer frame arrives. Holding it takes a third borrowed sample on the input's source topic, so a graph whose `latest` input reads an external topic another process already created with the default two fails at build, naming the count. On an input read through a second subscriber that counts arrivals (`block`, `sample(N)`, or a node library without the unified drain export), the step fires the node only while the input's own subscriber still holds a frame, so a frame an earlier read already took fires nothing more; `NodeEntry` gains `probe_trigger_input` and `probes_trigger_input` (`TriggerProbe`, non-exhaustive) for that question. A `#[cerulion_node]` node answers it; a raw-FFI node library answers it by exporting `cerulion_node_probes_trigger_input`, returning a positive value, beside `cerulion_node_sync_head_op`, whose op code 0 then answers for the input; a hand-written entry answers it by implementing `probe_trigger_input` and returning `true` from `probes_trigger_input`, which defaults to `false` whether or not the entry implements the per-set Sync head ops. A node that cannot answer it is named once at graph build. `consume` on a non-trigger input, and `consume = latest` on any input of a `sync_window_ms` or `unbounded_sync` node, are compile errors, and the `cerulion` commands that read a node's source refuse the same forms. A cdylib carries the declaration as an additive `"consume":"latest"` input key, so cdylibs built earlier load unchanged, and a host built before this change loads such a cdylib's input as `fifo`, with a warning naming the unknown key. Replay reproduces a `latest` input's reads and fires, and the fire re-derivation of a free-run recording holds a `latest` node to at most one fire per step, and to exactly one on a step whose drain popped a frame unless the node declares `throttle_ms` or its input is read through a second subscriber.
- `cerulion topic type <TOPIC>`, `cerulion topic find <TYPE>`, `cerulion topic bw <TOPIC> [--window N]` and `cerulion topic list -t` (also `--show-types`), the counterparts of `ros2 topic type`, `find`, `bw` and `list -t`. `topic type` prints a topic's `package/Type`, local or remote, read from one message. `topic find` takes `package/Type`, `package/msg/Type` or a bare workspace `Type` and lists the local topics of that type and the remote ones whose robot catalog names it (`--local` reads local topics only). `topic list -t` prints each row's type after the topic name, LOCAL rows from one message within one shared one second wait and REMOTE rows from the robots' catalogs, with `[unknown]` where the type is not known; plain `topic list` output does not change. `topic bw` prints once a second the payload bytes per second over the newest `N` messages (default 100, from 2 to 100000), in decimal units, measured from the messages' wire stamps.
- A graph's `network:` block can choose QUIC for the cross-host link. The carrier is the locator's first segment: `quic/<host>:<port>` is QUIC over TLS 1.3 with one stream per priority, `quic/<host>:<port>?mixed_rel=1` adds a datagram link on the same connection and port, and `udp/<host>:<port>?rel=1;mixed_rel=1` is QUIC with no encryption and no peer authentication, for a WireGuard overlay that supplies both. TCP stays the default. A new `tls:` block names the PEM files (`certificate` and `private_key` for a `quic/` listener, `root_ca` for a `quic/` connect, which also checks that the certificate names the host or IP it dials); a self-signed certificate can be its own `root_ca` when it is not marked `CA:TRUE`, and a `quic/` or `tls/` listener whose certificate is marked `CA:TRUE` refuses to start, naming the file and the `openssl` flag that mints an end entity. `cerulion-netd` reads the same files from `CERULION_NETD_TLS_ROOT_CA`, `CERULION_NETD_TLS_CERTIFICATE` and `CERULION_NETD_TLS_PRIVATE_KEY` and checks them at start-up by the graph rules (absolute, readable PEM paths, a listener certificate not marked `CA:TRUE`, a certificate and key for every `quic/` or `tls/` listen, a root CA for every `quic/` or `tls/` connect, certificate and key together, no file that no `quic/` or `tls/` locator reads, a carrier this build compiles); `cerulion-netd` refuses to start, naming the variable, on any of them or on a datagram-only locator in `CERULION_NETD_LISTEN` or `CERULION_NETD_CONNECT`.
- `CERULION_UNENCRYPTED_QUIC=on` (opt-in, read by `cerulion-netd`) listens on zenoh's unencrypted QUIC carrier, `udp/<host>:<port>?rel=1`, beside every `tcp/` listen locator on the same port, advertises it in the mDNS record as `udp_rel=<port>`, and dials it first: at start-up netd checks each discovered peer that advertises it, and each `CERULION_NETD_CONNECT` locator written that way, over UDP, and dials it over QUIC when it answers or over `tcp/` on the same port when it does not, with one warning that starts `QUIC FALLBACK:` and names the locators and the reason. The check waits at most `CERULION_NETD_QUIC_PROBE_TIMEOUT_MS` (default 1000, at most 6000). Explicit `tcp/` locators are used as written. This QUIC has no encryption and no peer authentication, the same as `tcp/`. What it changes is congestion control: a Linux TCP connection that idles longer than one retransmission timeout restarts from its initial window, while the QUIC stack has no idle reset, so a large message sent about once a second does not pay the extra round trips. With the setting unset, nothing changes.
- A graph's `network:` block takes `default_reliability: reliable | best_effort` (default `reliable`), the put reliability of every `egress` entry that sets no `reliability` of its own. An entry's own `reliability` wins in both directions, and an entry may set `reliability: reliable`, so one topic can stay reliable under a `best_effort` default. Graph-load validation refuses a `best_effort` default on a graph with no `mixed_rel=1` locator, as it refuses a best-effort topic, and an unknown value is a parse error naming it. The receive path is unchanged.
- An `egress:` entry can be a map, `{topic: /r/scan, reliability: best_effort}`, beside the bare topic name it was. A best-effort topic is put with zenoh's best-effort marker and rides the QUIC datagram link of a `mixed_rel=1` connection, so a lost frame is not retransmitted and later frames are not held behind it; every other topic is put at the block's `default_reliability`. Graph-load validation refuses a best-effort topic on a graph with no `mixed_rel=1` locator, a `quic/` or `tls/` locator without the certificate files it needs, a `tls:` file no `quic/` or `tls/` locator reads, a `tls:` block that sets no file, a locator whose carrier this build does not compile (`ws/`), and a datagram-only locator (plain `udp/<host>:<port>`, `udp/...?rel=0`, `quic/...?rel=0`), which sends every message once with no retransmission, so a reliable topic or one of zenoh's own declarations would be lost with the packet; the refusal names the reliable spellings `udp/<host>:<port>?rel=1;mixed_rel=1`, `quic/<host>:<port>?mixed_rel=1` and `tcp/`. Graph load warns when a best-effort topic can reach a peer over a locator with no datagram link.
- One message file types a port in both languages. A workspace's `schemas/<pkg>/msg/*.msg` files and `schemas/*.yaml` schemas generate into the Rust message crate beside the built-ins (`native_ros2_messages::<pkg>::<Type>`, a package-less YAML schema at the crate root) and into the Python `cerulion.msgs` namespace (`from cerulion.msgs.<pkg> import <Type>`), by the one resolution rule the runtime uses, so the type, its layout and its wire hash agree. `workspace create` and `workspace init` set `CERULION_WORKSPACE_MSGS` in `.cargo/config.toml`; an existing workspace adds `CERULION_WORKSPACE_MSGS = { value = ".", relative = true }` under `[env]`. `node create` and `node modify` now scaffold a Rust port of a `.msg` store type, which they used to refuse; in a workspace without the setting it is refused with the line to add.
- Python message classes: every message is a class in `cerulion.msgs` (`from cerulion.msgs.sensor_msgs import LaserScan`), and every view of a schema is an instance of its class, nested fields included. The wheel ships type stubs for the built-in packages; `cerulion node build` writes a workspace's stubs to `.cerulion/python/cerulion-stubs/`, as does `python -m cerulion.msgs`. `SchemaSet.message_type(name)` returns the class of any schema set.
- `cerulion graph pause <RUN>` and `cerulion graph resume <RUN>` hold a live run at its next step boundary and stop its clock, so timers neither skip ticks nor burst on resume and a recording shows no gap across the pause. A run's `run.json` records `"paused"`, and the viz daemon's `runs` rows carry `"paused": true` while a run is held. A run that is never paused is unchanged.
- `cerulion bag play <BAG> --resim all --record-out <PATH>` writes the frames the re-executed graph published to a new bag: one channel per graph-produced topic, labelled with the schema the re-executed graph publishes, with its name and provisioning copied from the input bag's channel where it has one. It works with and without `--verify`. The path must not exist, so an existing file is refused with exit 2 and never overwritten, and a run that does not finish removes the partial file. The `--report` JSON gains a `record_out` field naming the written path; reports from runs without the flag are unchanged, and `report_version` is unchanged.
- `cerulion-wsd` creates and builds. `graph.create`, `node.create` and `schema.create` do what `cerulion graph create`, `node create` and `schema create` do and answer with the `version` of the file they wrote, which a graph or node edit can send as `expect_version`. `node.build` runs `cerulion node build` and streams cargo's compiler messages as structured `diagnostic` events (file, line, column, level, message, code), then a `done` event; a client that closes its connection cancels the build. The protocol version is unchanged: an older daemon answers the new verbs with `unknown_verb`, and every existing verb is as it was. `cerulion_cli_engine` gains `node_cmd::node_build_streaming`, and `node create`'s trigger-policy defaulting moved from the `cerulion` binary into `node_cmd::resolve_create_policy` so the daemon applies the same rules.
- `cerulion-vizd` answers a new `sample` request: the newest 1 to 20 messages of an attached topic, each as `seq`, `ts_ns`, `size`, the decoded `fields` where the schema is known (or `null`) and a one line `summary`. The daemon keeps frames only for a topic that is being sampled, drops the ring five seconds after the last request, keeps at most eight rings, and keeps no body larger than 16 KiB, so sampling adds no subscription and a bounded amount of memory. The control protocol version in the banner is unchanged; a daemon without the verb answers it with the structured unknown-method error. See `docs/user-api.md`.
- `cerulion-remoted`, the robot-side remote-access daemon, ships in every release archive, in the Debian package (`/usr/bin/cerulion-remoted`) and in the Homebrew formula. `install.sh` places it beside the CLI and links it with the other programs (see the install script entry under Changed); a v1.0.0 archive, which does not carry it, still installs, and removes a `cerulion-remoted` a later release left in the install directory along with its link. `--uninstall` removes it.
- `cerulion-wsd` can wire and unwire a graph and remove a node from it. `graph.wire` and `graph.unwire` add or delete one `inputs:` entry, and `graph.unstage` deletes a node entry. Each takes an optional `expect_version`, edits the file in place so comments and layout survive, and refuses a wire between different schemas (`schema_mismatch`) or removing a node other nodes read from (`would_break`, with the wires listed) unless `force` is set. The protocol version is unchanged.
- `install.sh --uninstall` (`curl ... | sh -s -- --uninstall`) removes what the script installed: the programs and libraries, the links that point at them and, when the env file names that install, the marked line in each shell startup file and the env files. A directory without the installer's marker is left alone. The sign-in, keys and settings in `~/.cerulion` and the Rust toolchain stay.
- A Python client, new in this release: `import cerulion` publishes and subscribes to topics on the local machine over the same shared memory as Rust nodes, with no copy on receive. Call `cerulion.connect()`, then `session.publisher(topic, schema=T)` and `session.subscriber(topic, schema=T)`. `subscriber.receive(timeout_ms)` returns a `Frame` whose `view()` reads fields in place, `with publisher.loan(...) as msg:` writes straight into the outgoing slot, and `cerulion.open_bag(path)` reads a finished `bag record` bag. Cross-host topics are not exposed yet. Build it from source with `cd crates/cerulion_py && maturin develop --release` (Python 3.11 or later); the release archives do not carry a wheel.
- Nodes can be written in Python. `cerulion node create <TYPE> --lang python` writes `nodes/<TYPE>/node.py`, a class decorated with `@cerulion.node(...)` whose ports are `cerulion.input(T)` and `cerulion.output(T)`, plus a cdylib that embeds CPython. `graph run`, recording and replay treat it like a Rust node. A Python node must declare `period_ms`, one `trigger=True` input or `sync_window_ms`; `--raw-ffi` and `node modify` refuse it. `node build` uses `CERULION_PYTHON`, else `<workspace>/.venv/bin/python`, else `python3`. `cerulion node new` is now an alias of `node create`.
- Python APIs take message classes. `cerulion.input(T)` and `cerulion.output(T)`, `session.publisher(topic, schema=T)`, `session.subscriber(topic, schema=T)`, `frame.view(T)` and `record.view(T)` take a class from `cerulion.msgs`; a quoted schema name is accepted with `schemas=` (and alone in a node port) for a schema with no class. `Frame.view` and `Record.view` take the schema first; a call that passes the schema set first is refused with a `TypeError` that names the replacement spellings, `view(LaserScan)` and `view('pkg/Name', schemas=schemas)`. A class used against a set that resolves its name to another hash raises `SchemaMismatch`. The `node create --lang python` scaffold writes `import cerulion` and typed imports.
- Node parameters: mark a plain field of a `#[cerulion_node]` struct with `#[param(default = .., min = .., max = .., description = "..")]` to make it a typed setting (`bool`, `i8` to `i64`, `u8` to `u64`, `f32`, `f64` or `String`). A graph sets it per node with a `params:` map on the node entry, for example `params: {gain: 0.5}`. Values are checked for type and bounds when the graph loads and are written into the field before `init`. `graph validate` prints a `params '<node id>'` line per node, and `node info` prints a `Params:` table. A recording keeps the values, and `bag play --resim` applies them.
- Launch arguments: a graph declares a top-level `args:` map. Each entry is a default (`side: left`) or `{default: .., description: ..}`, and it is used as `${name}` in `prefix`, an output's `topic`, an input's `source` and `params:` values (`$$` is a literal `$`). `cerulion graph run <NAME> side:=right gain:=0.5` overrides values for one run. A name the graph does not declare is refused with the nearest declared one, and a word without `:=` is a usage error. A graph with no `args:` loads exactly as before, and a recording stores the resolved graph.
- `#[input(accumulate)]` on a node input hands each fire every frame that arrived since the node's last fire, not only the newest. Frames come oldest first by publish time; read them with `self.<input>.iter()`, `len()` and `is_empty()`. `cap = N` (default 10, range 1 to 64) bounds what one fire holds; past it the oldest frames are dropped and counted in `dropped()`. An accumulate input never fires the node. It cannot be combined with `trigger`, `depth`, `backpressure = block` or `backpressure = sample(N)`.
- Generated message types keep a `.msg` file's constants and field defaults. `int8 STATUS_FIX=0` becomes `NavSatStatus::STATUS_FIX`, and `float64 w 1` or `int32[] ids [1, 2]` set the value that `Default` builds. Neither changes the wire layout or the schema hash, and a loaned output slot still starts zeroed. A constant or default that does not fit its type, or a constant whose name is not upper case, is a parse error naming the line. `cerulion_core::codegen` also reads `.srv` files (`parse_rossrv`, `split_rossrv`) into `<Name>_Request` and `<Name>_Response` messages.
- `cerulion_core::dynamic` converts any message to YAML and back using only its schema: `message_to_yaml`, `message_to_yaml_with` and `yaml_to_message`. Reading YAML enforces ROS 2 `string<=N` and `T[<=N]` bounds and names the field path in errors. A block copied from `topic echo` output reads back to the same message. `yaml_to_message_with` reads YAML with a `YamlDecodeOptions`: `missing_fields` takes `MissingFields::Required` (the default, which refuses a field the input leaves out) or `MissingFields::Zero` (which writes the zero value of that field, at any depth), and `max_body_bytes` refuses a message body past that limit with `DynamicError::YamlBodyTooLarge` before the reader builds more. The limit leaves out the alignment padding between variable fields, so a finished body can be up to seven bytes per variable field longer.
- `cerulion logout` signs this machine out: it removes the session and refresh tokens from `~/.cerulion/auth.json` (the account id stays) and then revokes the session at the account service. Every command that needs an account then starts a sign-in at a terminal, and is refused with exit 7 elsewhere (a script, a CI job), until the next `cerulion login`. It prints one line, `signed_out: account=<id>` or `not_signed_in`, and exits 1 if the file could not be rewritten or the service did not confirm the revoke.
- `cerulion workspace create <NAME> --starter obstacle_avoidance` creates a complete workspace from sources bundled with this CLI version: a laser scanner node and a safety controller node with their tests, and the `obstacle_avoidance` graph. `starter.toml` records the CLI version and compiler. Creation is atomic and refuses any existing path; on a filesystem without a no-replace rename (some network, FUSE, SMB or FAT volumes) it is refused with the reason.
- `--local` keeps a command on this machine. On `graph run` and `node run` it is the same as `--network off`. On `topic list` (where `--no-network` is an alias), `topic echo`, `topic hz` and `topic info` it skips remote discovery, the robot schema query and starting `cerulion-netd`, reading only publishers on this machine. On `topic echo`, `hz` and `info` it also refuses a topic that `cerulion-netd` or `cerulion connect` re-injected from a robot. `CERULION_NETWORK=off` still selects the same scope.
- `graph run`, `node run` and `ros2 attach` log one line when the run sends topics off the machine over `tcp/` from a Linux host whose `net.ipv4.tcp_slow_start_after_idle` is nonzero, the Linux default: a warning naming the locators when a per-run gateway's locators include `tcp/`, and an info line when the egress goes through the shared `cerulion-netd` session, which every networked run registers with whether or not a remote peer subscribes. On such a host the congestion window of an idle TCP connection decays toward its initial size, so each large message sent at a low rate pays a few extra round trips, a cost that grows with the path's round-trip time; measured over a 31 ms wide-area path, a 301 KB message once per second took 164.8 ms p50 on `tcp/` and 79.3 ms on `quic/`. The line names both fixes: the sysctl set to 0 on the sending host, or `quic/` on both ends. A run with no egress, a gateway with no `tcp/` locator, and any other host log nothing.
- Usage telemetry. The `cerulion` CLI sends usage telemetry, on by default, when the build carries a telemetry key; `cerulion telemetry status` says whether this build has one. A source build carries none, `POSTHOG_API_KEY` supplies one to any build, and `POSTHOG_HOST` changes the destination (https only). The first command that could send prints a notice on stderr and sends nothing; later commands send. To turn it off, use `cerulion telemetry off` (saved in `${CERULION_HOME:-~/.cerulion}/telemetry.json`), `DO_NOT_TRACK=1` (or `true`) or `CERULION_TELEMETRY=0`; `DO_NOT_TRACK` wins over `CERULION_TELEMETRY`, which wins over the file. `cerulion telemetry status` names the deciding setting, `cerulion telemetry on` turns it back on, and the verb needs no sign-in. See `docs/telemetry.md`.
- What the telemetry sends: one `cli_command_run` per command (`verb`, `subverb`, `exit_code`, `duration_bucket`, and `install_method` of `install.sh`, `deb` or `brew`, read from a marker the installer leaves: `.cerulion-provenance.json` beside the programs, or `share/cerulion/install.json` for the package and formula). Also `graph_run_started`/`graph_run_completed`, `node_build_completed`, `bag_record_completed`/`bag_record_failed`, `bag_replay_completed`, `resim_completed`, `ros2_bridge_started`, `connect_session_completed`, `pair_completed` and `cli_login_completed`, which carry only flags, counts, exit codes and size or duration buckets. Every event also carries `surface`, `env` (`prod` or `dev`) and `app_version`. Never sent: arguments, paths, names, URLs, emails or message contents; a value that looks like one, or is over 128 characters, is dropped. Events go to PostHog in one batch at exit, waiting at most 300 ms; on a slow network they are dropped, never stored. `telemetry`, `completions`, `bagd` and internal subprocesses send nothing.
- CLI telemetry events carry your Cerulion account id once the machine has signed in to a hosted account, and otherwise a random `anon:<uuid>` kept in `telemetry.json`; `cerulion-vizd` events always carry the random id. A machine's first `cerulion login` sends that random id with the sign-in request so earlier events join the account, and the CLI sends PostHog one alias event that links the two ids. A different account signing in replaces it, and deleting `telemetry.json` resets the id and the notice. `cerulion-vizd` sends `vizd_started` (`os`, `arch`) and a `vizd_heartbeat` (`uptime_minutes`) every 15 minutes under the same consent settings, and only when `POSTHOG_API_KEY` is set in its environment; a running daemon checks consent again before each heartbeat.
- `cerulion graph levels` ends with a chains block: the trigger edges that could run as one fused chain inside one process, and for every other consumer edge the reason it stays queued (`fan-out`, `separate-processes`, `opted-out` and others). Each `graph run` writes its own census under `chains` in `run.json`. A node entry may declare `fuse: false` to end a chain at that node. Nothing in the runtime fuses chains yet, so runs are unchanged.
- `cerulion bag play <BAG> --resim all` resumes a free-run bag that begins mid-run, such as a Flashback capture, when the recording holds one worker process. It restores from that bag's checkpoint and periodic firing deadlines. A mid-run free-run bag with several worker processes is still refused with exit 2; the message names the worker count and says to re-execute the bag from its start or capture a graph that runs in one process group.
- `cerulion_core` gains an opt-in `local-transport` Cargo feature for an app whose publishers, subscribers and gateway all run in one process, such as an Android app that cannot use cross-process shared memory. Publish and receive stay zero-copy inside the process, and a gateway still serves topics over TCP. With the feature on, `process_groups:`, cross-process initialization and native cdylib nodes are refused. See `docs/android.md`.
- Cerulion builds and runs on Android, API 30 or newer, arm64-v8a and x86_64, cross-built with cargo-ndk. That covers shared memory publish and subscribe between processes, and `cerulion graph run`, `topic`, `bag` and `cerulion-netd` from `adb shell`, with node libraries cross-built on a host. `crates/cerulion_android` embeds the runtime in an app. An Android gateway announces itself over mDNS and refuses LAN topic requests by default: `CERULION_LAN_ACCESS=open` (or the app's `lan_access` key) serves them, and other platforms default to `open`. - `cerulion-vizd` can load a robot's URDF model onto an attached `unitree_go/LowState` topic through two new control socket requests: `load_model` (`urdf_path`, `topic`, `model_id`, and 1 to 12 `motor_joints` in motor-array order) and `model_status`. The model is checked before any mesh file is read (fixed, revolute and continuous joints, one GLB, OBJ, STL or DAE mesh per link, at most 16 MiB of XML), its meshes are read within a 256 MiB budget, and it is then drawn at `models/<model_id>` with its joints driven by the measured motor angles. See `docs/user-api.md`.
- `cerulion-vizd` draws voxel-delta map streams. A `sensor_msgs/PointCloud2` whose fields are exactly `vx_<N>mm`, `vy_<N>mm`, `vz_<N>mm` (`int16`), `hits` and `op` (`uint8`), with `point_step` 8, is read as map edits rather than points. The viewer keeps the map under the topic as static tiles of height-coloured cubes, walls, outlines and the robot's trail. `attach`, `status` and `list` report such a topic as `VoxelMap`, where they reported `Points3D`.
- `cerulion-rcpd` is an MCP server that lets an agent read a running graph (`robot://graph`, `robot://state/{name}`) and call only the tools an `rcp.yaml` manifest declares, plus a built-in `estop`. Arguments are checked against each tool's `input_schema` before anything is published. Every call goes into a hash-chained receipt log (`--verify-receipts <log>` checks it), and every call that passes the checks is published on the manifest's `journal.calls_topic` (default `/rcp/calls`), so a recording replays with `bag play --resim all --verify`. `--http` needs `CERULION_RCP_TOKEN`. It is not in the release archives; build it with `cargo build --release -p cerulion_rcpd`. See `docs/rcp.md`.
- `cerulion-rcpd` answers a graph's requests for a second look at a wrist-camera frame with Jev, TypeSafe's System One model, through OpenRouter by default. With an `eyes.jev` section in `rcp.yaml` (route, pinned model, fixed question sets, frame topic, key file, region), a node publishes an ask naming a question set and a frame on `/rcp/eye/ask`; the daemon sends that frame unchanged in one request and publishes one answer per ask on `/rcp/eye/answer`, `ok` or the reason Jev is absent (`disabled`, `no_credential`, `unavailable`, `timeout`, `rate_limited`, `quota`, `throttled`, `refused`, `wrong_model`, `malformed`, `not_visible`, `not_recorded`). Before any request it refuses anything but one JPEG of at most 640 x 480 and 200 KB and 4,000 estimated input tokens, and holds requests to 2 in flight and 5 a second after a burst of 10; a reply after the 1.5 s deadline is never delivered. It answers at most 20 asks at once and 10 a second after that; an ask over that bound gets no answer. Each answer has an `eye.jev` receipt, carries `"provenance": "third_party"` and records what was sent except the image and the key; `--verify-bag <bag>` joins a recording's answers to the receipt log. A gate reads an answer against the exact ask frame it published, so an answer given for another ask, such as a recorded answer that `bag play --resim` re-injects for an ask that changed, reads as `not_recorded`, and `EyeAnswer::for_image` does the same for an answer that names another frame's image. The eye tells a played recording by the transport node its frames come from (`cerulion_bag_play`, or `cerulion_replay_` and the recording's identity): an ask from `bag play` or `bag play --resim` gets no request, no answer and no receipt, and a played wrist frame is never held, whatever their timestamps say. An ask's deadline runs from its wire timestamp when that stamp is at most 250 ms behind the host clock, and from when the daemon reads it otherwise, so a run resumed after a pause keeps its whole deadline. The key is read from a file only its owner can read; `cerulion-rcpd jev on | off | status` switches Jev and reports today's looks and the asks dropped unanswered, and the first time Jev is on, the daemon logs one line saying frames leave the robot, before the first frame does. The daemon opens the graph's ask and frame topics once the graph has created them and never creates them, so it can start before the graph. An eye that cannot start leaves the tools served. See `docs/rcp.md`.

A panic is contained: that node stops and does not run again, the rest of the graph keeps running and `state` stays `running`, but status used to show no sign of the dead node. The status JSON gains `node_failures`, a list in graph order of `{ "node_id", "message" }` objects (the node's graph id and its first panic message), and `[]` when no node panicked. - On an Android device, the embedded runtime's `tracing` lines and those of every node linked into the app library now go to logcat under the tag `Cerulion`, so a node registration error, a failed mDNS beacon or a teardown warning is visible with `adb logcat -s Cerulion`. A line reads `<target>: <message> <field>=<value>...`, and the levels map to logcat priorities `E`, `W`, `I`, `D` and `V`. A new start key, `log_level` (`"error"`, `"warn"`, `"info"` as the default, `"debug"` or `"trace"`), sets the lowest level written; any other value or a misspelled key is rejected with error code 3. Each start sets the level again, so a start without the key returns to `info`, and a start that fails after it set the level puts the previous level back. A release build of the app library compiles out `debug` and `trace` lines, whatever `log_level` says. `embed_nodes!` installs the logcat subscriber when Java loads the library, and `CerulionRuntime.init` installs it when the load did not. To keep your own global `tracing` subscriber, set it in your own `JNI_OnLoad` before calling `cerulion_android::nodes::register`; the runtime then writes nothing to logcat and `log_level` has no effect. A line logged through the `log` crate does not reach logcat. See `docs/android.md`, `Logs in logcat`.
- An Android app can read a node's output without a sink node of its own. List the topics in the start config under `subscribe`, an array of `{ "topic", "schema", "depth" }` entries, then call `CerulionRuntime.poll(topic, out)`. It takes the oldest message off that topic's queue without waiting and appends it to a `StringBuilder` as the same JSON object text `publish` takes, for example `{"x":1.5,"y":0.0,"z":2.0}`. It returns `CerulionRuntime.OK` after appending (only `OK` appends) or `EMPTY` (15) when the queue holds no message; `BUSY` means a start, a stop or another publish or poll is in flight, so retry; `DECODE` (14) means the message did not decode, and it was still taken, so the next poll reads the one after it; `RECEIVE` (16) means the transport refused to create or read a subscription. `depth` defaults to 10 and must be 1 to 16; when a queue is full the oldest message is dropped. A schema with a nested message or an array other than bytes, a duplicate `subscribe` topic, and a topic the app or the graph produces under another schema are refused with error code 3, and a start logs a warning for a `subscribe` topic that is neither an app `publish` topic nor a graph output. `poll` also reads a run whose graph `finished`, until `stop`, so the last outputs are not lost. The status JSON gains `subscribed`, with `polled`, `dropped` and `undecodable` counts per topic. A non-finite float reads as `null`. See `docs/android.md`.
- An Android app can keep some topics on the device while it opens a desk connection. Under `"lan_access": "open"` the gateway sends every topic the app serves; a start config can now list `egress`, an array of canonical topics, and a LAN peer receives only those. A demand for any other topic is answered `refused` and no frame of it leaves the device. `[]` sends no topic, and without the key an `open` gateway sends every topic as before. Under `"paired"` nothing is sent either way. Each listed topic must be a graph output or an app `publish` topic; a non-canonical, reserved, duplicate or unknown topic, or a value that is not an array of strings (`null` included), is refused with error code 3, so a bad list never means send everything. The catalog still names every topic the app serves with its schema and liveness, so a desk can see that a withheld topic exists but cannot receive it. A start with `egress` and an empty `listen` and `connect` builds no gateway, so the list has no effect and the start logs a warning. See `docs/android.md`, `Choose which topics leave the device`.
- An Android app can dial a desk instead of waiting to be dialed. The new `connect` start key takes an array of `tcp/<host>:<port>` locators, the mirror of `listen`, for a network that drops multicast or connections into the device. A desk that is not listening yet does not fail the start: the app dials it again in the background. A locator that is not a well-formed `tcp/` locator (`quic/` and `tls/` included), a duplicate, or a value that is not an array of strings fails the start with error code 3. A `connect`-only start builds the gateway, so `lan_access`, `egress` and `ingress` apply to the desk the app dials just as they do to a desk that dials the app, and `mdns` raises no beacon for a `connect` locator. Like `listen`, `connect` is fixed for the process lifetime by the first start: a later start with different locators returns `BAD_STATE`, so restart the app process to change them. - An Android app can let a LAN peer publish into the graph. A new start key `ingress` is an array of canonical topics (default `[]`); under `"lan_access": "open"` the gateway re-injects frames a desk or another device publishes on those topics into the graph inputs that read them with an absolute `source:`, and drops a frame whose schema hash differs from the hash those inputs declare (the first drop of a series logs a warning, and drops are counted in `schema_mismatch_drops`). - Android app frames are stamped from the runtime clock, and a caller can supply the stamp. Each frame `CerulionRuntime.publish` sends now takes its wire stamp from the same clock the graph and its nodes use (nanoseconds of `CLOCK_MONOTONIC`, the clock `System.nanoTime()` reads on Android; `SystemClock.elapsedRealtimeNanos()` is another clock and also counts deep sleep), and a recording keeps that stamp as the log time of each message. New `CerulionRuntime.publishStamped(String topic, String json, long stampNs)` stamps a frame with the time an event happened, for example a tap read with `System.nanoTime()` when it lands. A stamp in the past is taken as is. A negative stamp returns `INVALID_ARGUMENT` (3) at once. Otherwise the call checks the runtime state and the topic as `publish` does, with the same codes, and then a stamp more than one second ahead of the runtime clock returns `INVALID_ARGUMENT` (3) before the message is read. - `CerulionRuntime.publish` and `publishStamped` now take nested messages and arrays of every schema type, for example a `geometry_msgs/PoseStamped` with its `std_msgs/Header` or a `geometry_msgs/Twist`. The top-level value must still be a JSON object, unknown fields are refused, and the text must be strict JSON: comments, `NaN`, unquoted keys, a number past the `float64` range and duplicate keys are refused, and a bare `-0` reads as `0` (write `-0.0` for a negative zero float). - An Android app can host the paired remote plane in its own process, so a paired desk reads the app's catalog, schemas and topics from another network while `lan_access` stays `paired`. The plane lives in the new crate `cerulion_android_remote` because it links iroh; the app's runtime crate lists its host in `embed_nodes!` as `remote: cerulion_android_remote::Host,` (the node list may then be empty), and an app that does not do this links no iroh. Any other plane failure is `REMOTE` (18): no host linked, a relay URL that does not parse, a second runtime in the process while one plane serves, or a plane that stops on its own. `status` gains `remote`, `{ "endpoint_id", "bound_sockets" }` while it serves and `null` otherwise, and `CerulionRuntime` gains the constants `REMOTE_NOT_PROVISIONED` and `REMOTE`. A paired desk can read every topic of the app's transport (`egress` limits LAN peers only) and cannot publish into the app, and the plane refuses `restart` and `engage-estop`. - `cerulion topic pub`, `cerulion service call` and `cerulion topic snapshot` publish a message given as JSON or YAML text, call a service once, and save the newest frame of a camera topic as a JPEG. `topic pub <TOPIC> <TYPE> <MESSAGE>` fills each field the message leaves out with its `.msg` default or zero, publishes `--times` frames at `--rate` and prints one `published:` line; `service call <SERVICE> <TYPE> [REQUEST]` speaks the protocol ROS 2 nodes on `rmw_cerulion` serve and prints the response as one JSON document; `topic snapshot <TOPIC>` reads a `sensor_msgs/Image` in `yuv422_yuy2`, `rgb8`, `bgr8`, `rgba8`, `bgra8` or `mono8`, or a `sensor_msgs/CompressedImage` holding a JPEG. A `.msg` or `.srv` type in a store or workspace that names a nested type of its own package without the package (`Item` in a `demo_msgs` file) now hashes it package-qualified, as `demo_msgs/Item`, as ROS 2 and `rmw_cerulion` hash it, so bags recorded by, and peers running, an earlier cerulion report a hash mismatch for such a type. Built-in types are unaffected.
- `cerulion rcp <ROBOT>` serves a paired robot's `cerulion-rcpd` as a local stdio MCP server: an MCP client runs it as a stdio server and reads the robot's resources and calls its tools. It runs `cerulion-connectd rcp`, which dials the robot's new `cerulion/rcp/1` plane with this machine's device key. `cerulion-remoted` admits only a key on the robot's access list and checks every message against the live access list: the resources, `subscriptions/listen` and `tools/list` need the observe capability, `tools/call` needs the teleop capability and the operator role, and any desk on the access list may call `estop`. It forwards each admitted message to the robot's local rcpd over loopback HTTP with a bearer token and names the desk in the `x-cerulion-caller` header; rcpd receipts and journals the call under that identity. At startup `cerulion-remoted` creates `<state root>/remoted/rcp.token` (mode 0600) when it is absent, a systemd environment file rcpd can read; `--rcp-addr`, `--rcp-token-file` and the `--rcp-*` bound and timer flags change the link. The ops act verbs, the ops verb `restart` and the rcp plane share one e-stop latch, and LAN ingress does not read it. An `estop` over rcp engages the ops e-stop before it is forwarded, so an unreachable rcpd still leaves it engaged, and so does an `estop` sent within `--rcp-drain-ms` after rcpd restarts and loses the session, which is answered with an error. While the ops e-stop is engaged, `topic-publish`, `service-call` and `restart` are refused with a verb error, and every rcp tool call except `estop` and `estop_clear` is refused with error `-32001` `refused: the robot's e-stop is engaged`. The ops e-stop clears only when `cerulion-remoted` restarts: while it is engaged, rcp `estop_clear` is refused with `refused: the robot's ops e-stop is engaged; it clears when cerulion-remoted restarts`, and once it is clear `estop_clear` reaches rcpd as any tool call does. Every message's access is checked when it arrives. An Observe or Act message's access, and the e-stop latch for a tool call other than `estop`, are checked again on the open connection to rcpd just before the plane sends it; an `estop` is not checked again. A `notifications/cancelled` reaches rcpd after rcpd has taken the tool call it names, or once `--rcp-head-timeout-ms` passes. Only the `cerulion-remoted` daemon serves the rcp plane; a process that hosts the remote plane as a library serves none. While `CERULION_NETWORK` or `--network` engages the desk's kill-switch, `cerulion rcp` is refused with exit 2 before any sign-in and before it resolves the robot, and `cerulion-connectd rcp` refuses before it binds an endpoint. `cerulion_link` gains `read_frame_or_end`, which returns `Ok(None)` only for a finish at a frame boundary.
- An ops `engage-estop` on `cerulion-remoted` also sends an `estop` tool call to the robot's `cerulion-rcpd`, so rcpd closes its own e-stop latch and refuses each mutating tool call it holds when the `estop` reaches it and has not yet published, including calls sent over `cerulion rcp` before the engage, and the graph receives rcpd's e-stop frame. It goes over the rcp plane's link (`--rcp-addr`, `--rcp-token-file`) on an MCP session of its own, with the reason `the robot's ops e-stop was engaged (engage-estop)` (the new public constant `cerulion_remoted::rcp::OPS_ESTOP_REASON`), and rcpd receipts every attempt under the identity of the first engager since rcpd last answered one. `engage-estop` answers without waiting for it, starts it before it writes its own log line, and the ops e-stop stays engaged whatever happens to it. Each attempt waits for each response head for `--rcp-head-timeout-ms` or 1 s, whichever is longer. The `estop` reaches rcpd once rcpd answers that its latch closed: while rcpd is not reachable, the token file fails its check or rcpd answers with an error, `cerulion-remoted` sends it again, waiting 100 ms after the first failure, twice as long after each further one and at most 2 s, and logs the first failure and the 10th, 100th and so on at warn and the others at debug. One such delivery runs at a time: an `engage-estop` while one runs starts none, since the one running keeps sending, and one that comes after the attempt rcpd answers began makes it send the `estop` once more. A delivery that ends before rcpd answers, at a stop by Ctrl-C or SIGTERM, a panic or a dropped runtime, logs at error, and at such a stop an attempt rcpd issued an MCP session first deletes it; a `cerulion-remoted` that is killed, crashes, or is ended by its hard-exit deadline or a second stop signal may end without that line. One that ends while it deletes the MCP session of an attempt rcpd answered that its latch closed logs nothing. `cerulion_remoted` now depends on `cerulion_wireclient`, for the sanitizer it applies to rcpd's text in its failure lines. To recover, as after an rcp `estop`, restart `cerulion-remoted`, then clear rcpd's latch with `estop_clear` under `limits.estop_clear: agent`, or delete `<receipts>.estop` and restart rcpd.
- The ops authorizer of `cerulion-remoted` classifies two e-stop verbs ahead of their handlers. `clear-estop` is admitted for the operator and owner roles and refused to a cloud device whether the robot's allow-from-cloud switch is on or off; while the switch is on the refusal reads `verb 'clear-estop' refused: the e-stop is cleared only from a device that is not a cloud principal`. `estop-status` is admitted with the observe capability. A refusal is receipted `Denied`, and until a handler is registered an admitted call answers `unknown_verb`.
- `cerulion_remoted::shutdown::ShutdownStage` is the stage `serve_planes` runs when its accept loop stops, after it drops its shutdown future: each `ShutdownParticipant` registered on `OpsServing::shutdown_stage` is driven to settlement in order while the ops receipt log is alive, and after a stop signal the endpoint too. One that fails, panics or is cancelled is returned as `RemotedError::Shutdown`.

### Fixed
- `cerulion-rcpd`'s `estop` tool queues the graph's e-stop frame before it logs a latch file or `intent` receipt it could not write. It used to write that error line first, through its synchronous stderr writer and while holding the lock that orders engages and clears, so a blocked stderr held the frame until the line was written. `estop_clear` now logs a receipt it could not write after it releases that lock, so its error line no longer holds an `estop` that waits for the lock. The error line for a receipt that could not be written, from any tool call or eye answer, is now also written after the receipt log's lock is released; an `estop` takes that lock before it queues its frame.
- A `block` producer whose consumer runs in another process is no longer held for good by a frame the consumer already read. The producer counted each frame on the edge's shared credit word after the frame was sent, and a consumer that read the frame and recorded its drain before that count found the word at zero, so the late count left the word one frame above an empty queue. At `depth = 1` the producer then deferred every tick, and only its stall warning, which named the consumer, said anything was wrong. The producer now counts a frame before the send makes it visible, on every publish path (a node's output, `publish_raw`, `send_raw_loan` and the overflow re-send), and takes the count back when the send fails. A consumer's drain that removes more frames than the word counts, which means some of them were never counted (native history to a late joiner, or a writer outside the graph on a `multi_publisher_topics` topic), now logs a warning naming the topic, `block credit drain removed frames its word never counted`, at the start of a run of such drains. The rest of the run is counted at debug level, except that the drain that takes the running total to each power of ten logs a second warning, `block credit drains still remove frames their word never counted`. A run ends only after a stretch of consecutive drains the word counted in full, and each end doubles the stretch the next run needs, up to 65536 drains, so an outside writer whose frames interleave with the producer's at most a few thousand drains apart logs only a handful of warnings, a writer whose frames are 65536 or more drains apart warns on each of them, and the first such drain after 65536 counted drains in a row warns again. The end of a run with counted repeats logs one line saying drains match the count again. This needs node ABI 31 (see Changed).
- `cerulion-remoted` stops gracefully on SIGTERM, which a service manager and `kill` send, as it does on Ctrl-C: it logs the signal, stops accepting connections, closes its endpoint and exits 0. Before, a SIGTERM ended the process at once, with no log line and none of that cleanup. The stop is bounded by `CERULION_REMOTED_HARD_EXIT_MS` (default 30000 ms), past which it exits with status 4, and a second Ctrl-C or SIGTERM during the stop also exits with status 4; either waits at most 100 ms for its queued log lines first. A stop that starts because the accept loop stopped on its own is bounded by the same deadline and exits 0 when it finishes, and the first Ctrl-C or SIGTERM after it exits with status 4. A shutdown participant that fails, panics or is cancelled makes the daemon exit 3; `cerulion-remoted` registers none of its own. Under `cerulion-netd`'s robot supervisor, a netd stop ends `cerulion-remoted` with SIGKILL unless it has already exited, so its graceful stop can be cut short there.
- `cerulion-remoted` no longer holds an e-stop on a blocked log write. With stderr full (a full pipe, a stalled journald), each thread that logged waited in its write, so an `estop` over `cerulion rcp` could wait before it reached `cerulion-rcpd`, an ops `engage-estop` could wait to answer and to send its retries, and a graceful stop could wait until the hard-exit deadline. The daemon now writes its log lines from a thread of its own, through a queue of at most 4096 lines and 1 MiB: a line that does not fit, or whose write fails, is dropped and counted, and no `tracing` line holds the thread that logs it; the iceoryx2 console logger and a panic message still write to stderr directly. Once stderr takes lines again, a warning names how many were dropped and, when more than one was, an info line says the log caught up. The count since the daemon started is the new `log_lines_dropped` field of the `cerulion/wire/2` `status` reply, absent from a host that embeds the remote plane; it leaves out the writer's own report lines and the lines an exit discards. Each exit waits at most 100 ms for the lines still queued, and counts those it discards in one error line. In Rust, `cerulion_wireclient::protocol::StatusReply` gains the public field `log_lines_dropped`, so code that builds one with a struct literal names it, and `cerulion_remoted` gains the public module `log_writer` and the same field on its `StatusReply`.
- The ops verb `restart` on `cerulion-remoted` is refused while the robot's e-stop is engaged or an engage is waiting for the control lease, as `topic-publish` and `service-call` are: it answers the verb error `unavailable: the robot's e-stop is engaged, so restart is refused` and stops and starts nothing. A device with the operator role could restart a graph, and so run its nodes again, while the e-stop was engaged. `restart` reads the e-stop before it reads its arguments, so the refusal reads the same on every host, and again after it stops the graph and before it starts it: an engage while the graph stops means the start command does not run, with `unavailable: the robot's e-stop was engaged during the restart, so the graph was not started again after its stop`. `cerud` gains `RestartStep`, the `RestartGate` trait and `RestartVerb::with_gate`, which ask a gate before each step; `RestartVerb::new` and `RestartVerb::with_runner` build no gate. `cerulion_remoted` gains `EstopLease::holds`, the e-stop read that the act verbs' refusal, `restart` and the rcp plane's Act check share, and the error text `ops::RESTART_STOPPED_NOT_STARTED`. `EstopLease::holds` reads the engage count again under the control lease's lock, so the act verbs' refusal and the rcp plane's Act check no longer miss an engage that counts itself in while they wait for the lock. A process that hosts the remote plane as a library still answers `restart` with `unsupported_host`. See `docs/rcp.md` and `docs/remote_plane.md`.
- `cerulion doctor`'s `cpu.governor` reported `cpuinfo_max_freq`, the hardware maximum, as the CPU's maximum clock, which hides the cap a power mode sets, such as a Jetson nvpmodel mode. It now reports each CPU cluster's governor, its clock now and the limits in force (`scaling_min_freq` and `scaling_max_freq`) beside the hardware range, says what holds a clock floor up (the power mode, `scaling_min_freq`, the `performance` governor, or a source it cannot tell on a Jetson whose power mode it cannot read), and names the latency cluster, the cluster whose floor holds the highest clock. On a Jetson it also reports the nvpmodel mode from `/var/lib/nvpmodel/status` and warns when that mode is one `/etc/nvpmodel.conf` does not define, as after an L4T upgrade that rewrites the file, since the next boot does not apply it. It reads files only and changes no clock. In `--json`, `max_freq_khz` stays the hardware maximum; the new readings are `scaling_max_freq_khz`, the per-cluster `clusters`, `cluster_governors`, `cluster_min_khz`, `cluster_max_khz`, `cluster_cur_khz`, `cluster_hw_min_khz`, `cluster_hw_max_khz` and `cluster_floors` (one value per cluster, joined with `;`, with `-` for a clock not read and `unknown` for a governor not read; a floor is `none`, `nvpmodel`, `scaling_min_freq`, `performance`, `raised` or `offline`), `latency_cluster` (the CPUs of the cluster or clusters tied at the highest floor, absent when no cluster has a floor, or when more than one cluster is online and every online cluster is tied there), and `nvpmodel_mode`, `nvpmodel_mode_name` and `nvpmodel_mode_defined`.
- An Android app now sees a remote plane that did not stop. `status.remote` keeps its `endpoint_id` and `bound_sockets` and adds `stop_error`, the reason the stop failed. Before, `status.remote` read `null` after a restart, a stop or a teardown after a panic whose plane did not close, so remote access was down without a sign. A restart still starts its graph. Every later start in that process, also of a new runtime and with or without `remote.enabled`, starts its graph and names the stuck plane in `status.remote`. A start with `remote.enabled` runs with remote off: it binds no plane and adds `off_reason`, which says why remote is off. Before, such a start failed with code 18. Remote off applies once a stop has failed: a start while the stop of another runtime still runs fails with code 18 and can try again. Every other bind failure keeps its code. Remote comes back after the app process restarts. See `docs/android.md`, `Host the paired remote plane`.
- A `cerulion-vizd` started while `CERULION_NETWORK` or `CERULION_VIZD_NETWORK` engages the network kill switch sends no telemetry; a daemon already running keeps the setting it started with, and `cerulion viz` says so when it reuses one under the switch. The docs, the switch's `--help`, the LOCAL-ONLY notices of a run and the fail-closed warns of a run or a query say what the switch covers: robots, relays, hosted Cerulion services and telemetry, not signing in, so the login gate's sign-in, `login`, `logout` and `account` still work under it.

- Under `rmw_cerulion`, an rclcpp intra-process subscription received each message twice when the topic also had an rmw subscription in the same process. Every take now fills `rmw_message_info_t::publisher_gid` with the gid of the publisher that sent the message, the gid `rmw_get_gid_for_publisher` returns for it, so rclcpp drops the rmw copy of a message it already delivered in process. A take that `CERULION_RMW_REPLAY` serves from a delivery log still reports the all-zero gid. The gid is the id of the publisher's iceoryx2 port, which every message the port sends carries: a message still queued from a publisher that has since been destroyed reports that publisher's gid, and a message a native node or a network gateway publishes reports its own port's id, which no rmw publisher holds.
- A Cerulion service server no longer keeps a reply publisher, with its shared memory, for every client it ever answered. It forgets a client whose reply topic has no subscriber left: when a request arrives from a client it holds nothing for, and when a response reaches no subscriber. A client in a process that crashed counts as present until iceoryx2 removes the dead process's ports. A client whose reply topic cannot be probed is kept, with a warning. `ServiceServer::tracked_client_count` reports how many clients the server tracks request sequences for, and `TransportManager::topic_subscriber_count_checked` returns a topic's subscriber count, or `None` when the probe fails.
- `cerulion graph run --record --single-process` refuses a graph whose nodes read a topic no node in it publishes, naming each topic and its readers, before any recorder starts. Such a recording stamped its own frames from a clock that starts at zero while the outside publisher stamped boot-monotonic time, so `bag play --resim all` did not inject the outside frames at the steps that read them and `--verify` failed. Record such a graph without `--single-process`.

It now parks only the first 200 µs block of each call and then sleeps in the kernel `ppoll` wait, as `CERULION_MONITOR_WAIT=1` already did on x86.
- With `rmw_cerulion`, the first rmw endpoint to open a ROS topic no longer decides the history and buffer limits of that topic for the other rmw endpoints. A subscription or a shallower publisher that opened a topic first made a later TRANSIENT_LOCAL publisher with a deeper history fail to open, with `DoesNotSupportRequestedMinHistorySize` or `DoesNotSupportRequestedMinBufferSize`; an rclcpp action server could abort when its client started first. Every rmw publisher and subscription now creates a topic with the same history limit, taken from the message type: 16, or 12 for types whose slice ceiling is above 16 MiB (`sensor_msgs/Image`, `PointCloud2` and unlisted variable types), with a subscriber buffer ceiling that holds it. A TRANSIENT_LOCAL publisher's depth is clamped to that limit, and a KEEP_ALL one asks for and reports the limit. Two processes that set different `CERULION_RMW_SLICE_CEILING` overrides for one variable type across 16 MiB derive different limits, and the one with the limit of 12 can still refuse the other's TRANSIENT_LOCAL publisher of depth 13 to 16, or of KEEP_ALL history. A native (non-rmw) Cerulion process that creates a ROS topic first still creates it without the limit, so a later rmw TRANSIENT_LOCAL publisher can still be refused there. Each publisher's shared-memory segment gains that many slots, plus 6 per subscriber slot at a limit of 16 (none at 12), as reserved address space, which is demand-paged: at the 4 MiB tier a VOLATILE publisher reserves 3.1 GiB where it reserved 2.3 GiB, more than a 32-bit process's user address space; at the 16 MiB tier 12.3 to 13.3 GiB where it reserved 9.1 to 10.1 GiB; at a 32 MiB ceiling 18.5 to 20.5 GiB where it reserved 18.1 to 20.1 GiB; and at the 128 MiB tier 20 to 22 GiB where it reserved 18.5 to 20.5 GiB (the upper figures for types that support loaned takes). A TRANSIENT_LOCAL publisher whose depth was above 12 at the 128 MiB tier reserves less than before. `cerulion_core`'s `TopicServiceConfig` gains `create_history_floor`; `TransportManager` gains `create_subscriber_with_history_request`; and `transport::wire_header_attribute` gains `HISTORY_FLOOR_ATTRIBUTE_KEY`, `with_history_floor` and `history_is_floor`.
- A Flashback capture of a live run no longer ends inside a step. A capture reads its trace and then its frames, so its trace could stop after a node's output was published and before the read that produced it was recorded; `bag play --resim --verify` then found no recorded read for the consult that produced that output and exited 6. The capture's trace now ends at the last step each rank's next boundary proves complete. A step that shares the final step's gating-clock target is removed with it, because their frames carry one stamp. Frames of the removed steps stay in the bag at their own step's target, after the covered range, and the capture manifest's `handoff.trace_end_cut` says how many steps were removed and why; a capture that leaves some rank with no complete step while another rank keeps one is not resimmable, and its reason names the rank; the `handoff.trace` sentence for a capture left with no trace now names the end cut too. A capture whose trace held only one step past its anchor is now not resimmable. `cerulion_bagd` gains `end_at_last_complete_step` and `CompleteSteps`, the rule the capture's trace end is cut by; in `cerulion_core::flashback::resim`, `ResimFacts` gains `ranks_without_a_kept_step` and `ResimGap` gains `RankWithoutCompleteStep`.
- A variable-schema generated reader no longer panics on bytes at an odd address. `HeaderShm::from_bytes(image.header_bytes())` panicked with `misaligned source pointer (need align 4)` whenever the writer had placed the nested header after strings or arrays whose lengths left it off a 4-byte boundary (a 1 MiB `mono8` `sensor_msgs/Image`, for one), and the frame reaches other nodes unchanged over the network and through `bag play`. `<Name>Shm::from_bytes` of a message with variable fields now never panics: a source aligned to the schema's new `<Name>Shm::READ_ALIGN` (the larger of its fixed section's alignment and its widest primitive-array element, 4 for `std_msgs/Header`) that holds the fixed section and offset table is read in place as before, and any other source, misaligned or truncated, is read from an aligned copy, with missing bytes read as zero. `from_bytes` of a message with only fixed fields still panics on a misaligned or short source. `CerulionSubscriber::spin_view_until_seq` now refuses a frame too short for its schema or not 8-aligned, as the other receive paths do.
- `cerulion bag play --resim` on a free-run bag no longer stands down the read-log-steered injection on a consumer whose recorded step took more frames than its input's declared depth (frames that arrived while it fired, pulled by the refill between fires). It used to report `queue_overflow` and fall back to the recorded-clock window, which could evict frames the recording delivered, hand the consumer nothing for several fires, and leave its reads off by the evicted frames. The replay now builds that input's queue as deep as the recorded schedule fills it, logs one line per raised input naming both depths, and reproduces the recorded reads. `queue_overflow` remains for a live producer's own connection over its depth and for a schedule deeper than replay will provision (16 frames on a `multi_publisher_topics` topic, the shared ceiling; 64 on any other, the deepest an input may declare). `cerulion_core` gains `GraphRuntime::build_with_schema_hashes_and_wiring` and `CrossProcessWiring::with_input_depth_floors`; in `cerulion_cli_engine::replay_inject`, `ConsumerEdge` gains `provisionable_depth` and `InjectionSchedule` gains `depth_raises` (`DepthRaise`).

Reliable topics now wait for the queue instead, for up to zenoh's `wait_before_close` (5 s by default), after which zenoh closes the link to that peer. Each egress topic has its own bounded send queue and sender thread, so a congested link holds up only the topics it carries, not the gateway's other links (closing LAN access waits for a put already under way). ### Changed
- `cerulion graph run`, `cerulion graph profile` and `cerulion bag play --resim` refuse at start a graph in which a `#[cerulion_node]` node declares an output that its entry in the graph YAML does not list under `outputs:`. The graph creates a publisher only for a listed output, and such a node failed every tick with `missing publisher for output`. `graph run` and `graph profile` fail the build with an error that names the node and the output and says to add the output with its `schema:` under the node's `outputs:`. `bag play --resim` exits with code 2 and says that the graph the bag embeds does not list the output. A Python node and a raw FFI node take a publisher only for an output they write, so their graphs are not refused. A macro node now reports this need: `NodeInfo` gains `with_publisher_for_every_output` and `publisher_for_every_output`, and the library info JSON gains the `publisher_for_every_output` key. A library built before this key is not refused. The embedded Android runtime keeps its own check, which refuses every node kind with the same message, and `cerulion_core::graph` gains `check_declared_outputs_listed`, the check both use.
- `rmw_cerulion` entity gids are host-unique. A publisher's gid is the 16 bytes of its iceoryx2 port id, little-endian. A subscription's or a client's gid holds the pid-namespace id in bytes 0 to 3 (0 where there is none), the process id in bytes 4 to 7 and the process's entity counter in bytes 8 to 15, all little-endian. Publisher and subscription gids used to be an entity counter plus the schema hash, and a client's a hash of its node name, its service name and an entity counter, so two processes could hold equal gids. A publisher's gid now changes from run to run, and a client's gid, and with it its reply topic, changes whenever the process id or pid namespace does.
- An `rmw_cerulion` subscription asks for retained messages by its own durability, as DDS does: a VOLATILE subscription receives no messages a publisher sent before it connected, and a TRANSIENT_LOCAL one receives up to its own depth, or up to the topic's history limit when its history is KEEP_ALL. A BEST_AVAILABLE subscription (rclcpp's `BestAvailableQoS`, Iron and later) receives what a TRANSIENT_LOCAL one would when the topic has at least one publisher as it opens and every one of them is a retaining publisher, and no retained message otherwise, including when the topic has no publisher yet; publishers in other processes count. This matches `rmw_dds_common` on Jazzy and later; Iron resolves the zero-publisher case to TRANSIENT_LOCAL. A retaining publisher is a TRANSIENT_LOCAL or BEST_AVAILABLE rmw publisher, or a native publisher that declares history; a BEST_AVAILABLE publisher now retains like a TRANSIENT_LOCAL one and reports its depth. Such a publisher carries the iceoryx2 port name `cerulion.retains`, so a publisher from a build without it counts as one that retains nothing. A VOLATILE subscription used to receive a TRANSIENT_LOCAL publisher's retained messages; it no longer does. A TRANSIENT_LOCAL subscription deeper than the publisher can receive more of the publisher's retained messages than the publisher's depth, up to the topic's history limit, and a TRANSIENT_LOCAL subscription can receive messages a VOLATILE publisher retained (DDS would not match that pair). A TRANSIENT_LOCAL publisher of a type above the 16 MiB slice tier, including `rcl_interfaces/Log` on `/rosout` (an unlisted type, so it takes the 128 MiB catch-all), now retains at most 12 messages where it retained 16. A publisher's endpoint info reports its depth clamped to the topic's history limit, the limit itself when its history is KEEP_ALL, and 0 when it is VOLATILE. A service an rmw endpoint creates states its history floor (the `cerulion.history_floor` attribute), and a native subscriber that asks for no particular history (a graph input, a Python `Subscriber`, `cerulion topic echo` and `hz`) takes no retained messages from such a service, so it does not replay a VOLATILE rmw publisher's last messages when it connects. Before, a terminal run showed the partition diff and asked whether to write it. Add `--yes` to save the layout into the graph YAML (with a `.bak` backup); `cerulion graph partition` still offers the interactive save. This changes the command's behaviour, which SemVer covers.
- The machine key moves from `~/.cerulion/desk.key` to `~/.cerulion/identity/device.key` (0600, in a 0700 directory). On first use an existing `desk.key` is adopted byte for byte, so paired robots keep trusting it, and `desk.key` stays, as a hard link to the same key or an identical copy; two different keys under the two names are refused, naming both files. The config directory itself does not move, but `cerulion pair` and `cerulion connect` now honour `CERULION_HOME` for the key, `robots.toml`, `config.toml`, `epochs/` and `ros2/` (they used to read `~/.cerulion` regardless), so move those files if you set `CERULION_HOME`. To start a new key, remove both key files.
- State records, the restore points a mid-run resume reads, carry the writing worker's rank and a format version, and their header grows from 32 to 40 bytes. A mid-run bag recorded by Cerulion 1.0 can no longer resume from its state records: `cerulion bag play --resim` refuses it, naming both format versions, and the fix is to record it again. Replaying such a bag from its start is unchanged.
- Re-executing a free-run recording with `cerulion bag play --resim` delivers each frame one node sends to another in the same worker process at the step the recording read it, and holds back a frame that arrives early. A recorded read the re-execution does not reproduce exits 6 and names the edge, the step and both sequences. A read log that cannot be enforced on such an edge is refused with exit 2. The `--report` JSON gains `read_log_enforcement`, always present, and `read_log_verdict`, present only when the read log finds a schedule divergence (exit 6). Lockstep recordings are unchanged.
- On macOS 14.4 and later, a worker process of a multi-process run that is waiting for data wakes on the publish instead of on its recheck timer: the publisher bumps a wake word in the topic's shared memory doorbell page, and the kernel wakes the blocked consumer. `CERULION_DOORBELL_OS_SYNC=0` turns this off on macOS only; `CERULION_DOORBELL=0` turns the doorbell off on every platform.
- One parser reads schema YAML everywhere, and it refuses three shapes that used to load silently, naming the schema: an entry that is not a mapping, a `fields:` written as a list (`fields: []`), and two fields with the same name. `schema info` on such a file exits with the error; `graph run`, `schema list`, `topic` and `node create` warn, skip that file and load the rest. An empty `fields:` is still valid.
- `cerulion ros2 attach --dry-run` runs from any directory, so listing a robot's DDS topics no longer needs a workspace. Outside a workspace it uses one empty temporary directory under `TMPDIR` and removes it on exit; if that directory cannot be created it refuses and says to point `TMPDIR` at a writable location or run from inside a workspace. Writing or running the bridge graph still requires a workspace.
- In `cerulion_core`, `DoorbellRegistry` loses `primary_addr` and `primary_topic`: look a topic up by name with `addr(topic)` or the new `bell(topic)` and `slot_of(topic)`. `CrossProcessWiring::with_sibling_topics` and `ValidationOptions::sibling_topics` take the new `SiblingProducedTopics` instead of a `BTreeSet<String>`, and a new `SiblingConsumedTopics` sits beside it. Both are built with `.collect()` from `String`s and serialize as the bare set.
- In `cerulion_core`, `DemandGetState::from_topics` is removed. Make the set with `DemandGetState::default()` and call `add_topic` once for each canonical topic.
- The viewer's 2D and 3D views always use the stage colour `#0b0d11` (it was `#10161f`), including views in a layout set with `set_blueprint`, which used to get the viewer's dark gradient. Point clouds coloured by intensity start at cerulean `#00c0ff` instead of pure blue; the green and red stops are unchanged.
- The README's Debian and Ubuntu recipe uses the archive at `https://apt.cerulion.com`. It installs the archive key only after checking its fingerprint (`953C69FD279D9256FA4B71C5DA5FDE5D0DC6D91B`), so a failed download no longer leaves an empty keyring that breaks `apt-get update`. A machine set up with the 1.0 recipe, whose `/etc/apt/sources.list.d/cerulion.list` names the older address, can switch by running the new recipe.

### Known issues
- On macOS, a node cdylib built against the released iceoryx2 0.10.0 can fail to create a port
  after the host closes a descriptor that node opened. iceoryx2 0.10.0 keeps a macOS-only table of
  shared memory descriptors in every copy of the library, the host and each node cdylib link their
  own copy, and a descriptor closed through a node's copy left a stale entry in the host's table,
  after which the host failed to create topics. The release binaries are built against a fork of
  iceoryx2 that repairs a stale entry in its own table, and workspaces made by
  `cerulion workspace create` or `cerulion workspace init` build their nodes against the same fork,
  so `cerulion graph run` with plugin nodes runs. A node cdylib built against the released iceoryx2
  0.10.0 keeps the unfixed table in its own copy. That includes every workspace made by Cerulion
  1.0, whose root `Cargo.toml` has none of the iceoryx2 `[patch.crates-io]` entries these commands
  now write: copy that block from a workspace made by `cerulion workspace create` and rebuild its
  nodes. Linux is not affected. The cause is eclipse-iceoryx/iceoryx2 issue 2034, and this note
  goes away when an iceoryx2 release carries the fix.
- Publishing a message allocates once, on every platform. The allocation is inside iceoryx2
  0.10.0, which builds a small shared cell per loan; 0.9.1 did not, and there is no way to avoid
  it through the library's API. It costs 14 to 19 nanoseconds and it is on the publish path, so a
  program with a hard real time budget should know it is there. The cause is
  eclipse-iceoryx/iceoryx2 issue 2035 and this note goes away when it is fixed.
- An app that embeds `cerulion_android` copies the iceoryx2 `[patch.crates-io]` block of Cerulion's root `Cargo.toml` into its runtime crate's `Cargo.toml`, also when it depends on the crate from crates.io: a patch applies only in the workspace that declares it, and a published crate carries none. `cerulion_android_remote`, the crate that hosts the paired remote plane in an app, is not published to crates.io, so an app that hosts the plane takes it and `cerulion_android` from git at one commit. See `docs/android.md`, `Graph nodes in an app`.
- An explicitly open LAN session does not authenticate peers. The `tcp/` carrier is not encrypted; `quic/` and `tls/` encrypt the link without authenticating its peer. A local-only run (`--local`, `--network off` or `CERULION_NETWORK=off`) cannot be served by another daemon on the machine, and a run's enabled `network:` block limits every serving plane to its declared `egress:` topics. Local readers and recording still work. Upgrade every Cerulion daemon on a machine together and restart running daemons. See `docs/networking.md`.
- The remote e-stop (`engage-estop`) does not stop motion by itself, and a restart of `cerulion-remoted` clears its engaged state. The e-stop does not gate LAN ingress either: while it is engaged and LAN access is open, a LAN peer can still publish into a graph's `ingress:` topics and into any topic this machine mirrors. A robot needs its own stop path, such as a hardwired e-stop. See `docs/remote_plane.md`.

## [1.0.0] - 2026-09-21

The first release of Cerulion. Its crates, binaries and Debian packages come from this tree.

### Changed
- The crates live under `crates/`, the tooling under `tools/`, and the user API reference under `docs/user-api.md`.
- The always-on window recorder is pinned and niced, and the dead-node walk left the live loop, so the multi-process round trip stays flat with the recorder on.
- A credit-blocked producer parks on the credit word instead of polling.
- A Flashback capture reads its frames after it snapshots its trace, and its coverage manifest marks every exit that left the close's final drain incomplete.
- The network posture pair and the service drain-all take halves were removed (ABI 21); services take one message at a time by design.
- Comments and documentation no longer carry internal tracker identifiers; the repository root holds the license, the readme, the changelog and the build manifests, with community files under `.github/` and legal files under `docs/legal/`.
- The default log filter is quieter: the per-topic producer reconciliation is one compact line of counters, the recorder's clean finalize keeps its one completion line, and startup, worker drain, exit hygiene and clean-finalize bookkeeping moved to `debug`, so `recording written to <path>` is the last line of a recorded run and a verification's `replay PASS` is no longer preceded by paragraphs of accounting. The long-running verbs still print their `info` lifecycle lines (worker spawn, trace ring and ready-file names, topic provisioning, daemon boot). The daemon's first-use spawn is reported at `info` (a boot still waiting after two seconds is reported at `warn`, so the quiet verbs are never silent for the whole readiness wait), the zenoh no-listener line is filtered by default, and a node cdylib announces its log filter only when `RUST_LOG` is set. The multi-process supervisor's planning build no longer prints a reconciliation line for a graph that never ran. Release builds compile `debug` out (`tracing`'s `release_max_level_info`), so the demoted lines are absent from a release build of `cerulion` (which hosts the recorder, `cerulion bagd`) and of `cerulion-netd` at any `RUST_LOG`; binaries built without cargo's `--release` keep them. The `debug-logging` cargo feature cannot lift that ceiling, and the documentation no longer says it can.

### Added
- Every `cerulion` command runs under an account. `cerulion login` signs a machine in once, with a short code to approve from a browser on any machine; later commands read the result locally and keep working offline. `login`, `completions`, `--help` and `--version` need no account.
- The release installer provisions the compiler that built the release. Every platform archive now carries the compiler metadata of its own build beside the binaries, and `install.sh` installs that exact rustc and its Cargo through rustup, verifies the full commit hash, and only then activates the binaries, so the compiler that builds your nodes is the one that built the CLI loading them. A failed setup leaves the previously installed binaries in place, though a partly installed Rust toolchain can remain under rustup's own management. Existing rustup defaults, profiles and shell startup files are left alone, `CARGO_HOME` and `RUSTUP_HOME` are honored, and an installation that carries Rust without rustup is refused rather than replaced. Archives from before the metadata still install their binaries, with a warning that they cannot set Rust up.
- The launch readme with the benchmark evidence packages, the benchmark charts on three platforms, the ROS 2 compatibility page and the second architecture panel.
- New workspaces select the compiler that built the CLI. `cerulion workspace create` and `cerulion workspace init` write a `rust-toolchain.toml` naming that release with the minimal profile, so `cerulion node build` inside the workspace uses it without an environment variable. The file is written only when a rustup toolchain whose release and full commit hash match the CLI is already installed; the check is offline, installs nothing, and leaves rustup's default alone. A missing, custom, nightly or beta compiler produces a warning instead, and an existing `rust-toolchain` or `rust-toolchain.toml`, symlinks included, is preserved. Workspaces created before this keep using an explicit `RUSTUP_TOOLCHAIN=`.

### Fixed
- A graph could abort with no panic text and no backtrace when the `cerulion` host and a node cdylib had been compiled by different rustc releases. A node crosses that boundary carrying Rust types whose layout the compiler chooses, and two releases can agree on every struct size and offset and still encode one of those types differently at run time, so the existing ABI-version check passed and the host then read a value the node never wrote and freed memory that was never initialized. A node cdylib now reports the compiler that built it, and the loader refuses a node whose compiler differs from the host's, naming both compilers and the two ways out: rebuild the node with the host's compiler, or reinstall the CLI with yours. `cerulion node build` also warns when the `rustc` on `PATH` reports a different release, while leaving Cargo's own compiler selection alone. This takes the node cdylib ABI from 21 to 22, so every prebuilt node cdylib must be rebuilt (`cerulion node build <type>`) before it will load.
- The examples cargo-check job skips the Go2 workspace and manifest-less directories; the fuzz job enters the crate at its new path.
